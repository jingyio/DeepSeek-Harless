# 从真实科研工作生成多工具、可增量任务

> 本文件是实例生成与验收方法，不是预写给 Agent 的工作流。目标是让研究者原本就要完成的决定成为可复跑的任务，并检验结构—语义分离、局部重复性和有界惯性。不得为了满足门槛制造论文、批注、邮件、会议或实验结果。未满足完整实例门槛时保留为局部实例。

## 1. 生成器的输入与两份输出

输入来自一个正在推进的研究决定，而不是工具清单：研究者的一句话问题、期限、读者、当前 Idea State／否决记录、允许访问的资料范围、原本的工作办法，以及已经发生或此后自然发生的事件。先做**元数据预检**，只列候选集合、笔记路径、数据文件和研究者指定的通信线索；研究者确认范围后才读取内容。私人材料、账号标识和完整轨迹留在 `.local/benchmarks/research-weekly-loop/<id>/`。

为同一实例生成两份互不混用的材料：

1. **Agent 可见执行包**：真实问题、完成标准、截止时间、来源与权限范围、可用工具、预算和当前已释放事件。只给结果要求，不给正确答案、固定检索词、规定的工具顺序、隐藏的未来事件或评分依赖图。Agent 可决定暂停、收窄或请求研究者澄清。
2. **评审用封存包**：来源版本与哈希、真实时间线、预登记的工具机会、主张—证据依赖图、可接受的多个决定及其证据边界、重大错误、后续事件和人工评审表。此包不进入 Agent 上下文。

## 2. 从候选池选题，而不是拼装剧情

每个候选先填以下五项；缺资料就如实标记。优先选择研究者本周原本要做、完成后能影响阅读、实验、论文或协作安排的决定。

| 项目 | 入选时应有的真实证据 | 缺失时如何处理 |
| --- | --- | --- |
| 决定 | 当前状态、至少两种合理行动及其取舍；允许“暂不决定” | 只有泛泛主题则退回定义问题 |
| 跨来源约束 | 文献发现的候选、Zotero 条目／批注、Obsidian 人工笔记中至少两个来源会改变同一主张 | 只做单源试点，不称跨资料任务 |
| 可复算环节 | 与决定有关的原始表格、运行记录或论文中的可定位数据及指标定义 | 只做定性调研；不得编造数值步骤 |
| 协作行动 | 研究者指定的真实 Gmail 线程／对象和讨论需要，或已有回复；有实际可安排的时间窗口 | 邮件／日历记为不适用，不计作遗漏 |
| 后续事件 | 可核验时间顺序的新批注、论文版本、实验结果、邮件回复或人的范围改动 | 只评初始交付；历史回放与前瞻试用分开 |

一个**多 MCP 完整候选**应使文献发现、Zotero、Obsidian、数值分析和 Quarto 在问题中自然有用，并且确有 Gmail／日历的协作需求；这不是要求 Agent 强制调用所有服务。当前本机 Zotero 是只读，归档写入以可审阅的 Zotero 导入清单或 Obsidian 笔记代替，不能假称已写入 Zotero。邮件发送和建会只在研究者审核后由对应服务执行一次；对照组只生成草稿，不重复对外动作。

允许先用[论文影响卡](mcp_paper_impact_cards.md)这类**轻量 MCP 核心任务**检验机制：每次一篇论文、一条研究主张、Zotero 批注与 Obsidian 状态，必要时加文献发现，输出可审阅卡片。它不需要人为凑齐 Gmail、日历或原始数据；不满足完整实例条件时单独计分。仍须至少三个不同决定的具体实例才能宣称跨任务 Motif 候选，在独立留出题上实际执行并与代码／缓存比较后才报告增益。

### 同类任务的最小实例数

每一种准备挖掘 Motif 的任务类型，**先冻结至少 3 个独立的具体研究决定**，再看重复子图。同一决定的 A/B/C 增量轮、改写提示词、替换模型、同一报告的三个段落都仍算**一个实例**。同一论文或项目中的三个高度共用来源的子问题，须标记为同一来源簇，不能充当跨项目泛化证据。

从原生 Agent 的真实调用轨迹中，在前两个实例寻找参数可重新绑定、守卫可验证的局部连通子图；第三个实例不参与编译，用来检验新实例上能否匹配、执行、交接并保持质量。三例都准备好后轮换留出实例，记录每轮具体来源、模型、工具 schema 与 Motif 版本。三例只能产生**候选 Motif**；要声称稳定收益，还需更多不同研究者、项目或时期的实例。不能因为三份任务卡写着相似步骤，就宣布已经挖到 Motif。

## 3. 四个机制门槛

这些是选题的**可观察性质**，不是给 Agent 的提示词。数值是首轮筛选目标，不是为了凑数而扩写资料；实际不达标时保留原任务并正确标注等级。

| 性质 | 首轮筛选目标 | 必须排除的伪复杂性 |
| --- | --- | --- |
| 中等语义依赖 | 有 2–4 个需要跨来源比较的有界判断，例如论文是否真的做了相同状态更新、结果是否可比、批注是否推翻旧主张；每处都能列出候选与证据限度 | 开放式“发明新方向”；或答案仅靠文件名、关键词和规则可推出 |
| 局部重复 | 至少 3 个真实来源要走相似的身份／版本／证据定位步骤；至少 2 条主张共享一个来源或计算节点。后续事件最好同时包含一处可安全沿用和一处应重新判断的旧结果 | 复制粘贴三份相同材料、预写整条 DAG、把旧答案当复用产物 |
| 不可压缩的依赖 | 预登记至少 4 条**输出决定下一步输入**的边：例如先识别论文版本才定位批注；核对指标后才判结果可比；形成具体缺口后才拟邮件；收到真实回复后才更新决定。保留能并行的分支 | 仅靠人工规定“阶段一结束才允许阶段二”，而阶段二实际不需要阶段一结果 |
| 有用的累积上下文 | 多种来源的版本、笔记、批注、数值、沟通与旧决定共同影响交付；记录每轮唯一证据量、重复送入模型的上下文量和来源定位。优先选择若全部原文平铺会超过一个简短单轮回答的实例 | 添加无关长文、重复粘贴材料或把长上下文本身当成功指标 |

依赖图只在评审包中保存。图中的节点是**可验证的资料／计算／行动或明确的语义缺口**，边须能说明参数或证据如何从上游传递。这样允许 Agent 自己选择并行调查路线，同时仍能检验它是否在依赖未满足时过早下结论。

## 4. 真实事件带与复用机会

- **A：冻结当前状态。** 记录来源版本、权限、哈希、主张、否决记录和时间切点；运行初始决定。文献路线与候选由 Agent 选择。
- **B：释放一次真实变化。** 例如新的 Zotero 批注、论文版本、数值文件或人的 Idea State 修改。评审包预先标明哪些来源／计算未变，哪些主张可能受影响；Agent 只看到事件本身。
- **C：若实际发生，再释放下一次变化。** 优先收集一类仅需验证后沿用的变化，以及一类有新科学含义、应打断旧路径的变化。没有这样的真实变化就不声称检验了惯性；合成扰动只能另列为回归测试。

每轮记录 `source_id + version/hash + permission + retrieval_time`、调用输入输出、主张依赖、语义交接原因、报告段落依赖。可跳过模型的条件是相关输入、指标定义、权限和守卫均通过重验；**来源正文未变并不表示没有新的反证**。新的论文、批注或人的决定默认触发有界语义复核。记录正确沿用、正确打断、错误沿用和无谓重算，而非只统计命中率。

## 5. 工具机会和强制验收

运行前为每项真实需求登记“前提、候选工具、贡献证据、替代路径”：

| 需求 | 自然工具机会 | 何时才算有贡献 |
| --- | --- | --- |
| 找新论文与版本 | arXiv／OpenAlex／开放全文，随后 Zotero 条目／批注 | 新来源改变候选、反证或阅读优先级；记录去重与版本关系 |
| 找回旧判断 | Obsidian 项目笔记、Zotero 批注 | 正确保留已否决方向、定位人的解释和原文证据 |
| 核查数字 | Python 或可审计的本地分析工具 | 从原始数据重算，写出定义、分母和输入哈希 |
| 交付与归档 | Quarto、Obsidian | 形成可审阅报告及可找回的 Idea Delta，段落有来源定位 |
| 澄清与安排 | 限定 Gmail 线程、Google 日历忙闲／待审事件 | 真实问题形成有依据的草稿或可行时间；实际发送／创建经研究者确认 |

报告每项机会的 `可用 → 暴露 → 调用 → 成功 → 对决定有贡献`，也报告必要却遗漏、工具故障和无用重复。允许 Agent 用原生本地工具完成等价操作，但要记录这会削弱哪类 MCP 的实测覆盖。工具数不是分数：至少先看决定质量和研究者修订时间。

### 让 MCP 在原生 DSH 中真正有机会被使用

上一次 Figure 7 任务把 PDF 和 JSON 完整复制进 Agent 工作目录，因此本地命令足以完成问题。下一轮保留研究者已有的资料位置：Zotero 批注仍在 Zotero、人的研究决定仍在 Obsidian、现有 Gmail 线程仍在 Gmail；执行包只给**经研究者圈定的集合／笔记／线程范围**和必要的本地原始数据路径，不预先把各应用的内容拼成一份大文本。交付要求指出实际依据的条目、批注、笔记路径、数据版本和引文位置；缺来源时允许报告未完成。公开论文可从文献发现工具定位，再核查与 Zotero 库中已有版本是否相同。

这是一种真实资料访问设计，不向模型规定“每个 MCP 必须调用几次”。Python 可经 MCP 或正常编程环境执行，Quarto 可经 MCP 或 CLI 渲染；是否使用某个具体入口由 Agent 决定。Gmail／日历只有在真实沟通、回复或排期存在时进入任务。运行前先用连接器健康检查确认这些服务可访问；健康检查调用不计入 Agent 自主轨迹。

运行后用 `scripts/report-tool-usage.py <session.v3.jsonl.zstd>` 汇总每类工具的暴露、调用及工具层成功／失败；再由评审逐项判定是否被后续决定实际使用。若任务需要的应用证据在执行包中明确存在，而原生 DSH 未查就下结论，应判来源遗漏并保留原始轨迹，不用操作员在中途提示“去调用某某 MCP”来修饰基线。可以另做一个**明确标为引导式产品变体**的试验，但不能与自由调用基线混报。

若资料确实留在应用中、MCP 健康检查通过而 Agent 仍系统性漏用，另加同题的**相关连接器预选**试验：由任务允许的来源范围静态挂载相关 MCP，再与全部工具可见的原生 DSH 比较。这是普通工具发现／上下文优化基线，不归功于 Motif；Motif 需要进一步证明能随执行依赖和新的语义缺口调整工具集合，且在相同质量门下带来额外收益。预选试验不得删除完成任务所必需的原生工具或证据入口。

## 6. 一个可交给原生 DSH 的任务类型

**题型：本周是否启动 idea 的最小反证实验，还是先收窄主张与补一篇关键论文？** 研究者给当前 Idea State、否决记录、一个限定 Zotero 集合与 Obsidian 项目笔记、一个真实原始数据源，以及期限。Agent 先恢复现场，自选文献发现路线，把新旧论文、人的批注和可复算数值合成一个有来源定位的决定；再生成 Quarto 组会简报和待审 Idea Delta。若研究者已有真实合作者线程及讨论需要，Agent 才准备邮件草稿并查询日历；若后来收到回复或新增批注，再做增量决定。

这只是**任务类型**。Model RSI 的“内部可更新能力状态”以及 AIDD 的“先选哪个应用与泛化设置”都可作为候选，但目前尚未确认完整的通信、数值和增量事件，不应把它们写成已经齐备的全链实例。上一次 Figure 7 诊断只有本地 PDF／JSON 和审查文件，适合测试数值复核与增量恢复，不适合代表多 MCP 科研闭环。

## 7. 运行与判断

先做连接器健康检查、来源冻结和预算预览，再运行**同题的原生 DSH**；不要把评审包、期望工具调用或未来事件给 Agent。保留模型版本、Flash／Pro 切换、每次请求 token／价格、工具轨迹、失败和人工提示；真实费用与供应商账单核对。第一次试跑产生开发诊断，不算留出成绩。

验收顺序：研究者和第二名领域评审先判断证据、数值、引文、Idea Delta 与下一步是否合格；再看工具机会召回、无效调用、人工修订与总成本；最后比较普通缓存／脚本、`research-workflow + 同一 Agent` 和 MotifAgent 对同一事件带的增量表现。若本题的依赖和重复不足、模型一次回答即可合格，或简单缓存已经达到相同质量与成本，就据实缩小机制主张。
