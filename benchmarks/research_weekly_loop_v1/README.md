# 研究 Idea 演进与证据闭环 v1

> 2026-09-25 修订。这里只冻结**任务协议**，尚未冻结真实资料实例或产生质量、成本成绩。首要评价是真正帮助研究者推进一个进行中的 idea；复杂性来自实际证据、批注和决定的交互，不靠强迫调用更多工具。

从真实项目筛选、冻结并验收多工具实例的具体方法见[任务生成协议](task_generation_protocol.md)；首批同类任务及准备缺口见[三题候选册](task_family_candidates.md)。更轻量的 MCP 核心试点见[论文影响卡任务族](mcp_paper_impact_cards.md)：每次只判断一篇论文如何影响一条现有主张。

## 要解决的日常工作

研究者已有一个尚未定型的 idea、若干被否决的表述、开放问题和散落在 Zotero／Obsidian 的论文及批注。一次真实工作往往同时出现：新论文与旧论文版本、某个重要负面结果、研究者给一篇论文新增批注、某个实验数据集的划分争议、与合作者的邮件澄清，以及 idea 范围变化。研究者要判断**哪些主张仍站得住、哪些该撤回、下一步该读论文还是该做实验**，并把决定留在下次能找回的地方。

Agent 的总任务不是“按模板填完每个文件”，而是在给定时间和预算内减少一个真实研究决定的不确定性：从现有 Idea State 出发，选择互补检索路线，吸收论文及人的批注，交叉核对支持／冲突／条件，更新证据与 Idea State，形成下一步可执行的实验或文献行动；后续真实事件到来时仅重做有依赖的判断。可以保持当前 idea、收窄、改写、暂停或否定它。**拒绝无依据更新也可能是正确结果。**

用户的 [research-workflow](https://github.com/jingyio/research-workflow/tree/55bbec71f888b3573ec295a0256bde05daf665a9) 已实现 Idea State、互补检索路线、论文卡、证据账本、矛盾记录、每周综合与状态快照。它是**必须比较的强基线**；公开仓库说明文献模块已实现，baseline 复现、数据集、实验和写作模块仍是预留接口。SSS 只有在同题质量、人工负担或合格交付成本上胜过“research-workflow + 同一 Agent／模型”时，才有增量价值。借用它的概念不能算 SSS 的机制成绩。

## 一个实例的真实输入

以研究者本来就要推进的 idea 为单位。运行前由研究者给出：

1. 当前研究问题、已承诺与已否决的表述、开放问题、最近一次人工决定；保留版本和时间。原始主张不能由 Agent 事后发明。
2. 一组真实初始资料：Zotero 文献及版本关系、关键批注、Obsidian 项目笔记、与此决定直接有关的 Gmail 往来；若涉及可行性或结果比较，另有真实数据／运行记录。只圈定研究者允许访问的集合，不默认扫描整库或整个收件箱。
3. 本轮**要做的决定**及期限，例如选定蛋白–配体还是抗体–抗原作为第一个任务、确定什么样的界面状态才可检验、决定哪个 split 能反映目标泛化。记录研究者若没有 Agent 原本会怎样做。
4. 读写和外部模型边界、预算、交付位置。原始私人文件保留在 `.local/`；对外模型只见经预览允许的摘录。

至少有两条相互关联但可分叉的主张，其中一条新证据可能影响多个下游结论，另一条可保持不变。此条件来自真实问题结构，而非人工植入“陷阱”。若真实实例不满足，就如实标为简单实例，不强行制造复杂度。第一轮先做一个真实试点；后续跨不同 idea 和研究者收集多例，开发过的实例不得再算留出题。

## 事件流：同一 idea 的多次交付

| 阶段 | 真实触发 | 必须做出的判断与产物 |
| --- | --- | --- |
| A：恢复现场 | 开始本周工作 | 对齐当前 Idea State、否决记录、旧论文卡／批注和来源版本；列出本轮最可能改变决定的开放问题及停止条件。形成只读来源清单和快照。 |
| B：互补调查 | 一个或多个开放问题仍可通过文献回答 | 动态选择 2–5 条互补路线；检索、去重、识别预印本／正式版、筛选支持与反证；为高价值论文形成可定位的证据与论文卡。遇到概念近似但任务或数据不同的论文，要判断能否比较。 |
| C：交叉综合 | 多条路线提供相容或冲突的信息 | 更新主张—证据账本、矛盾与缺口；区分论文声称、论文实测、邮件中的人类说法、批注和 Agent 推断。必要时用 Python 复算数字／检验数据泄漏，再决定哪些主张应支持、削弱、改写或保持未知。 |
| D：沟通与研究决定 | 关键细节尚需合作者／论文作者澄清，或已有邮件答复 | 在 Gmail 中定位限定范围内的真实线程，形成包含明确问题和依据的回复草稿；研究者逐封确认后才可发送。收到答复再判断它改变了什么，不能把邮件中的未经验证说法当作论文事实。用 Quarto 生成可审阅决策简报与 Idea Delta；确认后归档 Obsidian，并在 Google 日历中核对真实空闲时间、准备讨论安排。 |
| E：真实增量 | 随后真实出现邮件回复、新论文、修订、Zotero 批注、实验数据或人的 idea 改动 | 追踪事件关联的主张、证据和行动，重验受影响部分，保留无关且可复核的成果；写明撤回、修改、复用和未决内容。若事件推翻旧决定，重新开路线或转向实验；若只是重复或元数据变化，避免无意义重读与模型调用。 |

E 可以发生多次，且顺序不可预设：例如先由批注指出 split 泄漏，再有新论文提出近似的界面状态机制，最后研究者收窄应用范围。**不能事先编排虚构事件去冒充真实流**。若采集时间不够，可用研究者此前实际经历的版本与批注做“历史回放”，保留真实时间顺序并单独标记，不与前瞻试用混算。

**工具覆盖是场景筛选条件，不是调用次数指标。** 首批完整实例应选一个确实需要文献管理、项目笔记、数值核对、组会材料、邮件澄清与讨论排期的正在进行的研究决定，从而让 Zotero、Obsidian、Python、Quarto、Gmail 和 Google 日历都有合理位置。若某实例没有真实邮件对象、数据或排期，照实记录为局部实例，不为凑齐工具制造邮件、数字或会议。多方法对照使用同一封存邮件线程和日历空闲快照；只由研究者选定的实际工作流进行一次真实发送／建会，避免给同一联系人重复发信。

### 工具可达性与实际使用门槛

连接器清单数量不代表 Agent 能使用这些能力。当前普通 Harness 同时挂载全部已准备好的 MCP；隔离的 SSS 原生试验 Agent 则固定只见五个 SSS 入口。两者都尚未证明同一 Agent 能随 Motif 前沿改变可见工具集合，或在真实科研任务中按需组合文献发现、Zotero、Obsidian、Python／Quarto、Gmail 和日历。

每个试点在运行前登记**工具机会表**：当前决定中哪些证据或行动需要哪类工具、何时才具备调用前提、何种输出才算有贡献。运行时逐步记录工具的可用、暴露、调用、成功、被后续证据／决定实际使用的状态；同时记录需要但未被暴露／未被调用的工具、重复无效调用，以及模型未查资料就直接下结论的情况。不能用总调用数、工具种类数或 MCP 连接数替代完成质量。没有真实邮件或会议时，这些工具记为“不适用”，不能记为 Agent 漏用。

同题至少比较：①无工具单次模型回答；②同一模型看到全部可用工具的原生 Agent；③按当前 Motif 状态与语义缺口投影工具的 SSS Agent。三组固定相同来源、问题与评审标准，分别记录合格交付率、关键来源遗漏、工具机会召回、无效调用、模型请求与费用、人工修订和耗时。③的工具窗口由可执行依赖、授权范围与当前缺口决定，允许模型在缺口处请求扩大候选；不能把“当前阶段”写成唯一的固定工具列表。只有工具调用与 Motif 复用都在真实任务中发生，才评价它们的成本增益。

## 为什么它检验 Agent 与局部片段复用

固定 workflow 能完成“搜论文 → 写卡片 → 写总结”的常规路径；本题还要求在运行中判断**下一步走哪条分支、何时停止文献搜索、某个批注究竟挑战了哪条主张、什么实验比继续搜索更有信息量**。这些判断依赖语义和变化中的研究状态，不能仅凭关键词、文件时间戳或预设路线表确定。简单脚本可负责去重、哈希、字段校验和确定性复算，因此也列为基线；不预设它一定失败。

MotifAgent on SSS 的候选可复用片段是可执行的**工具／证据依赖子图**，而非一条完整固定流程：

| 候选片段 | 可能与什么组合 | 允许跳过模型的证据 | 必须交还语义判断的情况 |
| --- | --- | --- | --- |
| 来源身份、版本、邮件线程和批注读取 | 任何检索路线、旧论文卡恢复、协作澄清 | 同一来源版本、邮件消息 ID 和批注哈希，读取结果及权限未变 | 标题相似但内容不同，正式版改变关键结果，新邮件或批注有新含义 |
| 证据定位与引文重验 | 表征、物理、数据、负面证据等路线 | 旧引句仍在相同来源版本、相关主张和候选范围未变 | 新来源可能反驳旧结论，旧引句存在但不再充分 |
| 论文卡字段与数据复算 | 不同论文／数据集，接到主张账本前 | 字段有可核验出处；相同输入与脚本哈希得到相同数字 | 方法等价性、任务可比性、泄漏解释、科学含义 |
| 证据账本与依赖失效 | 某个主张影响 idea、阅读队列和实验方案 | 已批准的映射及依赖签名不变；只更新机器可证实的状态 | 一个批注跨主张、冲突证据、idea 范围变化、新路线选择 |
| 报告结构与已核验段落 | 多个主张合成组会材料 | 未变段落依赖的来源、主张、约束、引用全部重验 | 新证据改变总体判断、段落间论证或推荐行动 |

上述是**待实现／待证实的候选机制**，不是当前 SSS 已有能力。跳过模型调用必须有日志：被跳过的语义工作是什么、依赖签名为何相同、哪些引句和约束重验成功、是否仍需人工复核。仅因为文件未变不能跳过“是否出现新反证”的判断；新增科学证据默认进入有界模型／人工审查。若质量门发现漏失效，跳过记录计为失败而不是节省。

**示意轨迹，非预制答案**：一篇论文同时服务“界面状态是否新颖”和“数据划分是否可信”两条路线；来源识别与引文定位片段只运行一次，两个主张分支分别做语义判断，再合成实验建议。稍后研究者只给该论文增加关于数据泄漏的批注：来源身份、未受影响的表征证据和对应论文卡字段可重验后复用；数据分支、跨分支结论及实验建议必须重新判断。若后来只是 Zotero 元数据修正且论文正文与批注未变，可复用已核验的科学判断并跳过相应模型调用。实际实例只有发生这些事件且通过人工质量门，才可计入复用收益。

**惯性也需要反例。** 在真实事件中分别观察：旧来源和约束未变、允许继续执行的局部路径；以及新反证、问题改写、权限变化或工具失败，要求打断旧路径并重新判断的情况。历史工具顺序只可用于提出下一步候选，不能单独授权工具调用或沿用旧科研结论。若一个实例只有“资料未变”的事件，它只能检验缓存；若只有大范围推翻，它也无法检验局部复用。事件须真实发生或来自可核验时间顺序的历史资料，合成扰动仅作开发回归。记录候选路径、守卫、交接原因、错误延续率与错误打断率，并与普通脚本／缓存比较，才能判断惯性控制是否带来独立收益。

## 固定输入、交付物与评分

每个实例存于被忽略的 `.local/benchmarks/research-weekly-loop/<task-id>/`：`task.md`、按时间释放的 `events/`、来源／版本／权限／哈希清单、每方法的运行轨迹与账单、匿名评审、研究者实际决定。公开仓库只放匿名化协议与汇总，不放个人笔记、PDF、批注或运行日志。

每次交付至少有：① 可回溯的 Idea State 差异和版本；② 主张—论文—页码／段落—邮件／批注—推断关系；③ 冲突和未决问题；④ 阅读／停止／转实验的理由；⑤ 待确认邮件草稿、日历讨论建议及研究者能实际执行的下一步；⑥ 对上次报告逐主张的变更说明。报告和账本必须互相一致。不得让 Agent 看到未来事件、人工答案或本轮评分。

**质量先于成本**。两名领域评审盲评：关键论文和反证是否遗漏；引句是否真支持主张；是否混淆任务、数据集、split 或量纲；Idea Delta 是否有足够依据；否决方向是否被无证据复活；下一步实验是否能证伪当前假设。重大事实错误、虚构引文、未经依据的路线大转向，均为不合格。争议保留并由第三人仲裁。研究者另记录：人工核查／修订分钟数、决定是否采纳、一周后是否找回证据和真正执行的行动。若正确结论是“暂不更新”，也可合格。

**成本与机制**分开记：任务准备、授权、人工阅读、模型请求数、缓存／非缓存 token、真实费用、工具调用、失败与重试、端到端时间，以及每次 E 事件的复用／失效节点。只在交付质量达标时比较每份合格交付的总成本；漏掉反证的低价结果不算收益。额外计算“可安全跳过的模型请求中实际跳过比例”和“错误跳过率”，由人工审核抽样核对。不能把缓存命中 token 减少等同于人民币节省。

## 必须公平比较的组

1. 研究者现有手工流程：记录真实耗时与最终决定，不强迫完全同一写作格式。
2. **research-workflow + 同一 Agent／模型**：按其原有状态、路线、卡片和账本流程运行。它是最重要的工作流基线。
3. 通用 Agent + 相同 MCP／资料权限，以及确定性脚本 + 同一生成模型；检验通用自由调用和简单缓存是否已经足够。
4. SSS：迁移后的 MotifAgent 运行内核 + 同一语义模型与工具；再做关闭局部复用、只保留窄上下文／缓存等消融。
5. WorkBuddy 可作产品体验基线；模型或工具权限不同则单独报告，不能归因于 Motif 机制。

各 Agent 组冻结相同的初始任务、事件释放顺序、可读资料范围、模型版本和预算；实际工具能力不对齐时如实记录，不以平台缺失代替算法失败。开发实例、历史回放和未来留出实例分别报告。现有 [DR³-Eval](https://github.com/NJU-LINK/DR3-Eval)继续作为多文件报告质量的公开交叉检查；它不能代替这里的 Idea State、批注、跨轮变化和实际科研行动评价。

## 局部先导实例与完整实例的当前缺口

[试点任务卡](pilot_task.md)采用用户公开 research-workflow 中正在演进的 AIDD 方向，不复制私人 seed。公开 Idea State 和开放问题是真实问题来源，但公开仓库里的论文池与证据账本目前几乎为空。AIDD 的真实 Zotero 批注可用于局部试点；其邮件、数值数据、讨论和后续事件是否存在还未确认，因此不能把它当成首个完整实例。完整实例按[筛选协议](full_instance_selection.md)从研究者正在推进的决定中选择。SSS 当前已接入几个 MCP，但还没有完成 Motif 主控下的模型驱动全链执行，见[连接状态](../../src/mcp/connectors.md)。先登记真实实例并让现有 research-workflow 基线跑通，再测 SSS 的可验证局部复用。
