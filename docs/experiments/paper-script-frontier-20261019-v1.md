基于 `3943894`，独立分支 `codex/paper-script-frontier`。沿用本地真实 API 测试授权，不推送、不提 PR、不部署、不改私人原件和生产认证库。原始配置、轨迹、失败和账本保存在 `.local/script-frontier-20261019-v1/` 及按 run-id 分开的私有实验目录。

## 问题、假设与实现范围

本轮检验：当当前输入已经可以结构绑定时，让模型只确认一次“这个认证片段是否是当前任务所需”，Runtime 能否连续推进片段，并避免逐步生成代码和调度。假设只涉及可执行控制片段，不假设短输出天然意味着更低总费用，也不将历史频率当任务需求。

此次落地的是 Typed Mediation 的一个窄切片：**当前片段必要性的枚举选择 + 文件参数自动绑定 + 验证后连续执行**。没有实现任意文献身份判断的 `candidate_id` 填充、从自由文本自动产生全部查询参数，或通用 `all_cited_references` 范围求值器。不能把一个片段描述为完整论文校对自动化。

复用已有 Python `StructureHandoffRequest / SemanticResolution / resume` 的约束原则，在线实现继续使用 TypeScript，并挂接原生 Harness 循环：

- `script_execution_frontier.ts` 只从已认证库的真实前驱 `program_id` 关系发现片段。当前只接纳 2–8 个无分支、同文件输入契约的只读脚本；网络/标量选择、循环和歧义边不被自行扩展。没有手工写论文题目的 DAG。
- 结构层绑定当前唯一输入、哈希与库版本，暴露可选片段和缺失的当前需求选择。模型通过已有 Bash 返回 `geneloop-resolve` 的小 JSON；工具 schema 数量不变。
- 允许 `selected / unknown / ambiguous / unneeded`。后面三种不会执行；选择非候选、额外代码字段、管道、旧 request-id、过期/伪造回执和变化的输入均拒绝。
- 当前选择获得可信回执后，Runtime 在每个原生 provider continuation 边界发出认证脚本调用；只有结果及输入版本验证通过才推进下一步。中途不再询问模型，不用 embedding 猜测下一步是否必要。模型仍处理后续事实判断与最终报告。
- 已验证的当前缓存 Evidence 可以满足片段中的已有节点，不重复计算；输入变化后旧完成状态不再提供当前证据。当前用户消息变化立即取消片段，防止维持旧目标。
- 一个任务最多提出两个新版本片段请求。完整上下文、原工具集合和推理模式保留；没有为每个槽位另起子模型请求，也没有通过截断上下文制造低费用。

这与普通批量缓存存在能力重叠：两步片段若仅共享输入而没有输出到参数的数据依赖，普通缓存也可能一次完成。实验必须比较该基线，不能把两个 verified skips 直接称为两次净节省。

## 已观察的路径与失败

1. 首次真实 Execute：模型用 **1 次完整请求、110 输出 Token** 确认当前片段。该请求输入 20,108 Token，其中 KV 命中 13,696、未命中 6,412，代理可见估费 $0.00213778。Runtime 随后连续完成两脚本，**2 次真实 provider continuation 被跳过**。确认请求仍计入总费用，不称为零成本决策；没有同决策反事实实验，不能宣称输出减少百分比。
2. 首次三个完整任务分别在 39/6/6 个 provider 请求后因 HTTP 502 失败，每次均有 1 请求缺 usage。不能据此比较完整任务效果；保守预留全部保留，不把无 usage 视为零费用。
3. Execute 重试暴露结构绑定遗漏：文件被模型解压到 `/work/outputs/unz`，旧绑定器只扫描 inputs/code，因此没有候选。确认原因后通过原生任务取消接口停止，记为**局部诊断**，不混入完整任务成本比较；取消时 1 个 pending 预留未结算。未因停止而清零。
4. 修复：共享虚拟路径映射覆盖当前 `workspace/outputs/code`，Python 离线来源与 TS 在线绑定一致；拒绝非规范路径、越界和符号链接。多个同类型输入仍要求唯一绑定；变更输入仍拒绝旧计划。该修改服务一般工作区路径，没有写死题目或文件名。

### 对用户“Baseline 是否少做必要工作”的核查

**确有不同交付路径和质量门槛，不能把 101 vs 286 直接解释为同质量执行效率。** 两组均有 37 条逐条报告，不是简单漏掉整批条目；但 Baseline 通过通用 `export_review_report`，Execute 主要走 `stage_current_audit → finalize_current_audit → export_current_audit_pdf`。这些工具在两侧均可用，路径由模型选择，实验没有强制某一侧选择它们。

| 按完整请求可见动作归类 | Baseline 请求 / USD | Execute 请求 / USD |
|---|---:|---:|
| 报告协议 | 6 / 0.04728873 | 187 / 0.23749180 |
| 其余所有类别 | 95 / 0.11511981 | 99 / 0.13387750 |
| 合计 | 101 / 0.16240854 | 286 / 0.37136930 |

报告类别差 **181 请求**，总差 **185 请求**；报告费用差 $0.19020307，解释约 91% 的总费用差。这是观测归因，不证明是 sidecar 导致模型选择了这一条路径，也不证明 181 次全部可无损消除。

具体证据：

- 通用导出 `SessionReport.export` 校验当前来源哈希、段落形状和版面；它不运行 `validate_audit` 的条目编号、来源 ID、状态枚举、引用检查完整性校验，回执明确 `scientific_content_certified:false`。这是现有产品允许的接口，不应指控 Baseline 作弊；但它不足以作为本实验的合格质量门。
- Execute 报告类 187 次工具调用含 stage 148、finalize 27、read 6、结构化 export 4、通用 export 2。27 次 finalize 全被拒绝：**9 次 invalid_status_priority，18 次 duplicate_source_ids**。stage 有 54 次 MCP 执行错误，另有 5 次重复键、2 次确认无来源、1 次批量超限、1 次额外字段的显式拒绝。这些不能全算必要科研核验。
- 代码检查确认：stage 允许写入随后才在 finalize 拒绝的状态枚举及重复来源；sources 只追加；已有 citation_checks 不允许覆盖（重复提交会报错）；`read_current_audit` 只能读已定稿报告，不能读草稿。由此形成“写入有误 → 定稿失败 → 无法检查/定点修复 → 重复试写”的恢复陷阱。LLM 最终声称 citation_checks 接口全坏，但轨迹和代码不支持这个笼统判断；已存在键再次写入也会失败。
- Baseline 的实际 6 页 PDF 首段写“30 个唯一引用键、41 处命令”，同段又称“39 条书目记录全部被引用”；同源去注释、解析字面 cite/citet 命令结果是 **58 处、37 键**，Bib 库 39 条、bbl 37 条。PDF 后段与最终文字仍有“无列而未引”和“仍有未被正文调用条目”的矛盾。其较低费用不能视作合格费用。
- Cache 最终引用的 5 页 PDF 写 65 处引用；优先级摘要又声称“35 条有标注、2 条为 —”，同时列 P1=1/P2=18/P3=4，相加仅 23。仍不合格。
- Execute 存在一份 5 页 Bash 自制 PDF，已抽取全文并检查各页缩略图，但未通过当前结构化交付收据；不能以“磁盘存在 PDF”改判成功。Baseline/Cache 还分别留有一页概要或排版试验 PDF，必须与最终全文分开，不能把 summary 的全部 pdf_files 当有效完整交付。

评审为本轮代码/轨迹/源码计数/PDF 文本与逐页缩略图检查，**不是独立人工盲评或 37 条真实性的完整外部复核**；人工修订耗时未计量，未代替模型修稿。上述反例已足以否定合格同质量比较。后续应统一三组最终验收谓词及交付版本，允许各组用同样有效的批量或确定性流程，不能强迫 Baseline 增加不必要模型调用来制造收益。
