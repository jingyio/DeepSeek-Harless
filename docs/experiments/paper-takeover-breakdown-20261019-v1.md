# 论文费用与 Runtime 接管障碍 Breakdown

- 实验 ID：`paper-takeover-breakdown-20261019-v1`，2026-10-19。
- 分支：`codex/paper-takeover-breakdown`，基于 `d71c603`；在线实现仍为此前冻结版本，未修改 Runtime、工具表、提示、认证库、生产或原始资料。未推送、PR、部署。
- 类型：对[上一轮](paper-negative-real-20261019-v1.md) **448 次真实请求**重新归因，并在新私有副本上重放受信工具方法和原 TypeScript Runtime。没有新增付费模型实验，不是新的降本或质量验收。

## 结论与下一步选择

当前只能接管初始 BibTeX 的两项检查，大多数高成本操作根本没有进入可执行候选集合：**脚本挖掘的形态/参数覆盖不足、认证后执行关系断裂、frontier 对候选的范围很窄，以及搜索内部请求在接管入口之外**，均比 embedding 阈值更直接。

“写脚本”中混合了大量当次论文的核验结果和报告文字，不能将其全部作为可缓存代码；报告路径又不一致，不能把多出的模型调用全部算成 Motif 的必要开销。Negative Motif 对已覆盖错误确有局部拦截资格，但它在工具执行阶段介入，此时模型已经生成参数并付费，不能直接把一次工具阻止算成整次模型请求跳过。

优先级据此修订：先针对真实重复读取/取证操作，补齐从当前 Evidence 绑定参数、不同输入之间的已认证依赖和模型请求前的续接；语义目标仍需当前授权或模型明确选择。草稿读取/修复只在它实际阻塞某段接管时做局部修补，**不先大改全部报告流程，也不扩大其他场景或先调 embedding**。负面机制应保留多个仍成立的失败条件，但仅做这个修订不足以覆盖主要费用。

### “写脚本”并非全是可复用算法

离线 AST 检查仅作为组成诊断，不按字符比例估算 token 或科研判断费用。例如 Baseline 写报告数据模块的 Python 源码 8,730 字符中，字符串值占 7,018；Positive 组装报告章节的 13,769 字符中，字符串值占 13,193。它们包含当前论文的数据、标题、来源及解释，并非都能替换为固定代码。

两次请求分别估费约 $0.005878 / $0.008348。可复用的是数据搬运、排版、计数等逻辑；当前论文的事实解释仍需语义判断。相同 AST 骨架也不证明字面值可以随意替换，诊断不会据此发布算子。

## 为什么 Runtime 没有接管

### 1. 库有 7 个算子，自动路径实际只覆盖 2 个

直接调用原 `learnedScriptFragments()` 检查冻结库，结果是一个两节点片段：条目/重复键/括号统计 → 重复标题/缺字段。

| 认证算子 | 个数 | 当前接管资格 |
| --- | ---: | --- |
| 唯一两节点片段中的算子 | 2 | 当前语义确认后可自动连续执行；两组真实运行均完成 |
| 未组成多节点片段的单节点算子 | 4 | 不被当前 frontier 提议；其中两个的历史前驱未认证入库 |
| 带 argv 的网络取证算子 | 1 | 被 frontier 排除；只能由模型显式选择并填写当前参数 |

两个前驱分别因 sandbox 重放失败、任务特定字面量未参数化而未入库。整个认证报告保留了 16 个拒绝：9 个任务特定字面量、6 个 sandbox 重放失败、1 个历史 stdout 不复现。不能以补 ID 或放宽认证来拼接它们。

`script_execution_frontier.ts` 还要求相邻算子消费完全相同的输入契约。`.bib` 单文件检查不能自然接到 `.tex` 引用提取，再接 `.tex/.bib/.bbl` 交叉检查；当前参数流没有表达这种关系。纯 shell 的读取、管道和组合命令也不在 Python 单调用编译器的覆盖内。

**两次跳过不是“最多只准跳过两次”的限制**，而是当前只有这段两节点片段。不能把请求邀请数量上限与节点跳过数混淆。

### 2. frontier 结束后，不进入普通匹配

`script_motif_runtime.ts` 的 `intercept()` 在 frontier 分支内：ready 时接管，否则立即 `next()`。它不会继续执行下方普通结构候选/embedding 匹配。因此调相似度不能使其余算子获得执行机会。

Positive 的片段完成后还有 **159 个请求 / $0.251277**，占该组费用约 98.8%；正负面组完成后还有 **89 个请求 / $0.139703**，约 97.7%。这不是说上述全部可以接管，而是说明已发生的接管只覆盖开头很小一段。

### 3. 大量命令未能成为可复用候选

把付费请求中的调用交给现有静态编译器诊断：

| 主要诊断障碍 | Baseline 请求 / USD | Positive 请求 / USD | Positive + Negative 请求 / USD |
| --- | ---: | ---: | ---: |
| shell 形态不在单 Python 调用挖掘范围 | 80 / 0.082856 | 46 / 0.047239 | 23 / 0.019738 |
| 未绑定路径/任务字面量或缺少受约束输入 | 9 / 0.008419 | 17 / 0.016240 | 9 / 0.008909 |
| 当前静态编译可产生候选，但不在冻结库 | 8 / 0.005417 | 9 / 0.010219 | 6 / 0.006442 |

表中“主要障碍”按完整请求归类，混合调用另列；不是算子安全可执行率。这项诊断读取的是最终工作区，不能还原所有历史边界文件版本。`saved_source_changed`、二进制输入和语法等其他拒绝保留在逐请求记录，不假称它们在当时一定应当通过。

三个完整任务共发现 23 个静态候选调用，含引用键提取、`.bbl` 编号和跨文件比较等。但这些还没有独立输入认证、当前语义目标和参数流，不能仅凭“能编译”就替代模型请求。新候选与旧算子 ID 不同也不证明语义一定不同，当前 frontier 未进入语义匹配路径才是更直接的限制。

### 4. 一部分请求根本不经过该 Runtime

搜索工具内部辅助模型请求不经过外层 `llm/stream` 的 Script Motif 续接。三组分别 3/8/13 次；正负面组约 $0.043171。它们含检索相关性与摘要等语义处理，不能盲目跳过，也不能仅扩大 Bash 库就消除。

显式 `geneloop-cache` 同样需要模型先生成调用，正负面组实际有 2 次、约 $0.001383；语义确认各花 1 次请求、约 $0.002249/$0.002284。缓存复用本身不自动减少这些选择请求。放开单节点候选若仍需每次单独确认，也可能只是“花一次确认，换一次执行”，必须计算净收益。

## 错误恢复与 Negative Motif

### 实际轨迹与重放严格分开

真实完整任务中，Positive 未启用负面库，却发生 17 次可匹配的结构化失败：批量上限 2、重复引用键 2、非法枚举 1、重复来源 ID 12。启用负面库的完整组没有发生这些结构化失败，所以没有负面提示或早停。**这组零触发主要是路径差异，不是现有相关字段规则完全识别不了错误。**

在新副本上直接调用原 `PaperOutput.stage/finalize`：Positive 35 次暂存、13 次定稿，Recovery Baseline 6 次暂存、6 次定稿，Recovery Negative 1 次定稿，**61 次回执逐项一致**，含原始 SHA 与失败码。三个工具 schema 摘要也与原真实请求相同；未运行历史 Bash 脚本。

随后使用原 TypeScript Negative Runtime，对这些精确状态做观察性重放：

| 真实历史片段 | 假设提示送达后的工具拦截机会 | 未送达提示时 | 实际新增模型跳过 |
| --- | ---: | ---: | ---: |
| Positive 完整轨迹 | 10 | 0 | 0 |
| Recovery Baseline | 5 | 0 | 0 |
| Recovery Negative | 0 | 0 | 0 |

“假设提示送达”明确是诊断：把 Runtime 生成的 notice 放入本地请求对象，检查原 beforeRequest/guard；没有发送给模型，不改变历史后续选择或执行结果。**这些数字不是在线命中或可实付节省。** Positive 的 10 个机会跨 10 个不同草稿状态，支持字段条件能覆盖跨版本失败；不得转成“省了10次模型调用”。

### 已定位的两项控制缺口

1. **guard 在工具执行前、模型生成之后**。这 10 个调用所在的真实付费请求合计约 $0.009301，已经用于生成参数；拦工具不会退还费用。潜在收益只能来自后续避免徒劳恢复，必须通过真实 continuation 配对验证。它也不能直接解释 $0.130679 的整个失败后阶段。
2. **只保留一个 active failure**。观察到定稿的重复来源 ID 失败仍存在时，暂存又报重复引用键；后者替换了前者，之后暂存成功清空 active，下一次定稿仍失败但没有旧失败守卫。多种并存原因的学习已经有局部支持，在线记忆却仍只有一项，相关字段编译本身不能解决这个丢失。

### Bash 失败尚未进入负面编译

实际工具文本末尾的非零 exit 标记分别有 Baseline 11、Positive 7、正负面 5 次，原生 `isError` 均为 false。若只看原生异常会漏掉这类恢复；本轮另列文本标记，不把它当安全凭证或确定性原因。

负面离线采集只接受结构化 MCP 失败，在线 `observe()` 遇到 Bash 立即返回。因此这些 shell 失败没有进入现有负面规则学习。语法、依赖缺失、网络响应及数据处理错误不可混为一种可预测原因；仅解析错误文本不足以认证自动拦截。
