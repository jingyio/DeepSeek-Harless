# 多轮附件输入与视觉读取边界

2026-10-19。当前附件上下文与执行进度改动见[修复及验收记录](experiments/attachment-context-streaming-20261019.md)；前一轮 PDF/OCR 验收另见[历史实验](experiments/pdf-ocr-vision-20261018.md)。真实模型新验收状态以修复记录为准，不将历史结果冒充本轮结果。

## 已修复的输入行为

- 同一对话追加附件时，新任务同时取得此前原始附件和新附件。首次原生 Chat、后续私有任务、跨场景切换与服务重启使用同一套继承规则。旧上传回执被消费后，从该父会话持久文件卡片取得来源引用。
- 文件引用在任务接收时冻结；复制前检查长度和已有 SHA。相同名称和内容去重；同名不同内容保留两份，旧文件使用 `-previous-<摘要>` 后缀。原始文件和旧任务目录不改写。
- `/paper` 的历史交付筛选接受 DOCX/DOC。普通 Chat 在首个场景切换前生成的 `outputs/code/` 文档，也会先按原任务时间范围保存不可变副本。双栏结果按原来对应侧继承；单路 Chat 的同一结果可供两侧读取。新上传附件不会阻断历史交付继承。
- 原始附件优先。沿用既有场景文件容量；超过原始文件容量时明确失败，不悄悄遗漏比较对象。容量之外的历史派生结果会在任务上下文明确标记未带入，不能声称已读取。
- 网页保留用户原话和附件卡片；独立 plugin 资料不显示为人类消息。旧版混入人类消息的提取块只有与该 RPC 对应的持久原始任务内容一致才清理展示与迁移，用户自行粘贴同形 JSON 保留。原始日志与文件字节不改写。

来源仅取自当前账号、同一父对话的持久记录。交付再次核验任务/对照身份、对应侧、不可变索引和字节摘要；分支截断和原有权限边界保留。

## PPT/PPTX 的视觉与风格输入

原来仅按保存顺序提取文字；现在所有场景共用 `geneloop_presentation.py` 和 TypeScript 输入适配器，结合两类证据：

原生声明和实际画面分别记录：

1. PPTX 原生结构：保存页序、画幅、实际关联的主题/母版/布局、对象几何、占位符、字体与颜色声明。保留 scheme 引用，不假装已经完全解析继承、透明度和字体替换。它们是声明，不是像素观察。
2. 实际画面：由现有会话命令沙箱内的 LibreOffice 在新私有目录渲染，禁用宏和链接更新，并使用独立的无网络 namespace；原件只读。每页（包括只有文字的页）生成 JPEG，Flash 返回精确绑定原件 SHA、保存页号、`source_id` 的内容与 `style_observations`。错误页保持未完成，不用 HTTP 200 冒充已识别。最终回答仍用所选模型，Pro 通过辅助 Flash 看图，费用计入原任务账本。

二进制旧 `.ppt` 在同一隔离环境生成 PDF 和新的标准 PPTX；`normalized_source` 记录派生路径、SHA 与原件 SHA，供官方原生编辑流程使用，不改写原件。没有可用渲染器时，PPTX 仍可读取原生文字/样式声明，但不能声称看过画面；旧 PPT 明确报告缺少隔离转换能力。

用户给原始模板并要求沿用原生设计、替换内容时，GeneLoop 根据官方 ppt-master 路由选择 **Edit Native PPTX**，用 round-trip 导入/编辑/导出，语义选择参考页、重排或重复页面。仅借鉴风格重新设计或建立可复用模板工作区，分别按官方 Generate / Create Template 路线处理。宿主只提供证据和工具，不替模型挑页、写 SVG 或制作输出 PPT。原件和新内容在同一对话按已有规则继承。

视觉观察不等于保证精确复刻。缺失字体、Office 引擎差异、复杂效果、外链、视频和动画可能无法保真；静态预览不证明播放效果。本次没有把 PPT 图表转成经过核验的原生数值表，也没有增加备注提取协议；原生编辑技能可直接读取原件备注和对象。输出仍须实际渲染，并单独检查内容正确性、可编辑性和风格保留程度。

## PDF 上传现在如何处理

Chat、PPT、Paper、Data、Files 共用 `geneloop_pdf.py` 与 `sceneAttachmentContext`。PyMuPDF 按页读取原生文字；无文字页及只有少量页眉、主体为大幅扫描图片的页面自动调用本地 Tesseract OCR。混合 PDF 的扫描页不会因其他页有文字而跳过。中英文语言包固定版本和 SHA，原件只读，结果绑定原件 SHA 与页号。

所有页面均渲染为整页像素，包含只有文字排版表格的页；同时提供图注、当前页及相邻页正文和固定来源观察指令，交给 Flash 做图文分析。该指令不含当前用户问题，避免问候引发重新审阅。Pro 不接收它不支持的原生图片，而是取得 Flash 的来源绑定分析，最终回复仍使用用户选择的模型。文字提取成功不再被当作图片已经读过；逐页 `visual_content_reviewed` 和覆盖计数只在实际分析成功后设置，失败页面明确标记。

PPT 的版本化 MCP 逐页阅读和 Paper 的 PDF 阅读也使用同一 OCR 读取器。PPT 不重复注入完整原生正文；仍通过固定来源的 MCP 工具读取，OCR 文字和图片分析则随任务提供。Data 的 OCR/图片观察不替代经过核验的原始表格单元格或独立统计证据。

OCR 不是完整视觉理解，也不保证公式、密集小字、扫描表格和数字准确。本次没有增加倾斜纠正、手写识别、OCR 置信度或逐字坐标协议；不能据此声称这些能力已完成。视觉页面最长边为 2400 像素，特别小的图例仍可能看不清；分析必须如实说明。扫描页仍保留像素供视觉模型交叉阅读。

OCR 在本地处理，不额外调用模型；图片分析请求使用同一已激活任务、同一累计预算与账本，按实际 Flash 模型统计费用。取消会中止 OCR 子进程或等待中的视觉请求，已发生的上游费用继续结算。原生网页的首次所有文件上传均进入现有后台单路任务，先接收用户原文和文件卡片，再处理附件并发布真实读取进度。成功页按原件、代码、依赖和渲染/OCR资源版本在宿主私有缓存复用，不在普通问候中重跑。失败页保留细分诊断，重新上传同原件可重试；没有新增自然语言任意重读旧失败页的工具。

安装：先按 `requirements.txt` 安装 PyMuPDF，再运行 `python scripts/install-pdf-ocr.py --root <专用目录>`，配置 `GENELOOP_PDF_OCR_ROOT`。成员部署同时设置 `memberSceneDeployment.pdfOcrRoot`；启动时核对专用目录、语言包摘要和只读挂载。缺失 OCR/视觉能力时返回明确的逐页未完成状态，不伪造识别成功。

## Word 与 Excel 含图资料

DOCX、旧 DOC 和 XLSX 的正文/原始单元格保留；页面通过同一 Office 隔离渲染与逐页图像观察通路提供。图像观察不能替代单元格数据或独立统计复算，缓存公式不伪装成已重算。未支持的格式或缺失渲染资源明确返回实际状态；外链、宏、音视频不执行。原始原生图片及作为文件上传的 PNG/JPG 等均通过官方附件存储验证像素引用，跨场景承接时按接收后的真实身份去重。
