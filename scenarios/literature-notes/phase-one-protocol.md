# 第一阶段：三个完整任务的开发与实验准备

2026-10-12。任务定义在运行前确定；第一轮已完成，结果见 [实验记录](../../docs/experiments/phase-one-20261012-8a865a78.md)。本文是当前协议说明，实际首轮冻结版本及运行后修订均保存在私有实验目录，不替代有效配置快照。

## 输入与用户参与

使用现有 `testpdf/` 三篇实验论文，不要求用户新增论文、参考答案或人工审批。默认问题沿用：“这三篇论文的方法、实验证据和限制，对构建高效科研 Agent 有什么启示？” 两篇子集任务将题面中的“三篇”改为“所选论文”，其余要求一致；语料增量前后题面保持这个不依赖篇数的版本。

不修改原 PDF；论文、派生输入、原始事件、账本和输出只放忽略的 `.local/`。API key 继续使用已有加载入口，不进入题面、协议或日志。用户可以补充偏好的输出格式，但不作为启动条件；默认交付证据表、带出处的综合回答和显式缺口。

## 三个任务及成功标准

| ID | 输入和操作 | 自动验收重点 | 现有实现与缺口 |
| --- | --- | --- | --- |
| T1 首次比较 | 三篇原始 PDF；模型自主选择阅读范围，形成五字段证据表和综合回答 | 实际读取当前来源；每篇方法、实验依据和限制有出处或明确未报告；事实与项目推测分开；真实交付收据可重放 | 复用 `run-pdf.py`、支持审阅/修复或官方 Web 同 Session 流程；先选定共同入口，不能跨入口直接排名 |
| T2 缺口修复 | 先用 T1 的真实缺口；没有自然缺口时另存明确标记的受控诊断案例 | 找到指定缺口；补读后有证据地修订或明确无法回答；保留未受影响内容；综合回答与修订表一致 | 复用 `repair-pdf.py` 与现有来源校准工具；诊断案例须符合受信输入及收据校验，不能伪造原始运行事件 |
| T3 资料更新 | 在私有副本中用两篇生成基线，再加入第三篇；增加一个完全无变化的控制案例 | 新论文被纳入；旧结果没有被当作当前完整答案；过期来源不能被复用；无变化时重放校验后复用 | 自动来源绑定路线复用逐篇事实并使跨论文综合失效；遗留独立来源审阅路线保守复核旧论断。新反证对旧事实的语义影响检测尚未实现 |

三篇论文的子集与新增次序在运行前按稳定来源 ID 冻结；不根据最有利费用事后选择。T3 的新文件不是作者修订版，不能把该实验称为修订版变化验证。来源变化及撤回的既有测试只作守卫诊断，另报结果。

受控缺口只修改单独的诊断输入，记录原始来源、父工件摘要、修改位置和生成方式；评分参考与答案不进入 Agent 上下文。自然缺口与注入缺口分别报告。现有修复入口若不能接收这种有效诊断输入，先在场景内实现并测试适配，再运行，禁止绕过输入校验。

## 记录、质量与候选筛选

先用普通 Harness 建立完整轨迹，保留阅读、自动支持复核、补读、修复和综合各阶段的真实请求、token、估费、时延、拒绝及失败。重试、二次复核、离线回收恢复和首次基线构建费用全部保留；阶段划分是分析视图，不改原生事件。

自动结构/来源检查与模型语义审阅分别记录。没有人工审批不代表没有质量检查；通过自动检查不保证科学真值。记录错误归因、缺失条件/单位、未支持论断、覆盖和关键冲突遗漏；未完成独立来源支持核对时标明语义质量未验收，不宣称同质量降本。不能仅以撤回更多内容而得到更便宜的“合格”输出。

候选优先级由实际累计耗时、模型费用、返工及可验证性决定。可考虑跨任务复现的缺口定位/补读/再检查分支，以及变更/失效/更新分支；固定机械操作保留普通脚本。模型相关性判断、跨论文科学推断与证据支持判断不因工具重复就自动跳过。

## 对照与停止条件

先完成三个任务及统一验收，再只为最高优先候选开展普通 Harness、实际 Code Mode、普通脚本与 learned Motif 的同任务配对对照。每个任务各组的来源、问题、工具能力、自动质量门槛、重试及上下文策略相同；缓存状态分开报告。当前 Code Mode 仅证据准备组件已经验证，完整任务接入尚未完成，不能据此声称四组全任务对照已经可用。

新 Motif 必须来自正常训练轨迹，独立认证后再测；已有三个已知论文任务属于开发诊断，不称跨论文留出泛化。旧证据准备 manifest 不可直接改名适配新工具。学习、认证、未命中、失败与回退费用计入。若同质量下不优于脚本，保留脚本作为默认，不强行启用 Motif。

付费阶段继续复用用户已授权的 DeepSeek API 和预算代理。启动前预览并冻结实际模型、配置、工具/来源/代码摘要、预算与实验 ID。默认先准备并预览，只有显式 `--call-model` 开始付费。无 A100 依赖，不启动思考模式或更换前端。

在仓库根目录先运行 `node scenarios/literature-notes/run-phase-one.ts`，再用返回的私有目录运行 `node scenarios/literature-notes/run-phase-one.ts --experiment .local/<目录> --call-model`。总预算默认12美元，每任务默认3美元；结果目录存在时拒绝覆盖或重跑。预算是保护上限，非承诺开销。选定论断的追加支持检查使用 `repair-selected.ts`，默认预览，原始运行不覆盖。

## 开发顺序与接口边界

1. 复用现有入口完成 T1，并保存完整质量核对和阶段记录。
2. 从 T1 构建有效的 T2 修复输入及独立评分；冻结两篇基线及 T3 的来源变化控制。
3. 汇总三个任务的瓶颈；选择一个候选，先建立强脚本，再学习/认证并比较 Motif。

新增场景任务编排、受控缺口准备和选定论断修复；复用已有 Runtime、预算和真实收据，不改共享接口或上游 Harness。如果完整任务 Code Mode 需要共享接口变化，先列出字段、生命周期、兼容与收据来源，再实施并更新 GitHub 提交说明。

已有负面结果与边界见 [四组组件对照](../../docs/experiments/harness-strong-20261012-5da6ab9f.md)；扩充语料的后续设计见 [分层验收方案](../../docs/experiments/literature-evaluation-protocol.md)。
