# 基于图的智能体优化研究需求与初步实施方案

> **后续优先级已更新：** 用户随后明确将“合格任务的实际成本下降”置于图方法之前，并提出代码迁移和范围明确的 deep research 作为首批场景。请结合[场景与成本目标补充](场景与成本目标补充.md)及[场景筛选与成本对照](../experiments/场景筛选与成本对照.md)使用本文；本文件保留导师录音的初步整理。

> 用途：作为后续场景调研、原型开发和实验设计的工作文档。本文根据《录音原文.rtf》整理；录音中未说清或疑似转写错误的内容，放在文末待确认清单中，不作为已证实的事实。

## 一、讨论形成的核心方向

当前的首要任务是找到**真实、有代表性、团队能够自行部署和验证**的场景，证明基于图的智能体方法相比直接调用模型或现有智能体流程确有收益。之前的结果偏演示性质，下一阶段需要可试用的原型和可信的对照证据。

优先考虑两个通用场景：

1. **日常写代码。** 不把项目定位成只做“代码重构”。重构可以是写代码过程中的一个步骤，方法也可以只优化规划、检索、工具选择等部分步骤，但评价对象应是完整的代码任务。
2. **重复性办公工作。** 录音中提到邮件操作、计划同步日历、文献整理、文件整理、数据分析等候选流程。先选择团队日常确实会做、能让同学试用并给出反馈的流程。

场景不宜依赖企业内部数据或企业部署后才能判断效果。公开数据集可以用于可复现实验，但必须检查它与真实工作是否相符；自行编造的数据不能单独支撑有效性结论。

## 二、研究目标与要回答的问题

**总体目标：** 在代码和办公任务中验证，图方法能否在不降低任务质量的前提下，减少模型调用成本、执行时间或人工修正，并形成可复现的实验结果。

| 编号 | 要求 | 需要回答的验收问题 |
| --- | --- | --- |
| R1 | 场景真实且可由团队独立验证 | 不拿到企业私有数据，能否开展真实试用和可复现实验？ |
| R2 | 覆盖日常代码工作，而非单一重构任务 | 图方法介入某些步骤后，完整任务质量和效率是否改善？ |
| R3 | 至少覆盖一种重复性办公流程 | 流程是否有真实需求、稳定步骤和可核对的结果？ |
| R4 | 方法在关键决策点真正介入 | 能否记录图方法的输入、决策、执行结果及作用位置？ |
| R5 | 与直接调用模型或原有智能体流程公平对照 | 在相同任务、模型、工具权限及预算条件下，收益是否稳定？ |
| R6 | 同时评估质量、效率和真实使用感受 | 是否完整记录成功率、质量、成本、耗时和人工修正？ |
| R7 | 尽快交付可试用的最小原型 | 同学能否自行完成一次任务，并看到可解释的结果？ |

其中 R1—R6 是讨论中反复强调的方向；R7 是依据“尽快让同学试用”的要求整理出的实施建议。

## 三、场景选择与首批任务

### 3.1 代码场景

建议以“辅助日常写代码”为定位，首批任务覆盖不同工作步骤：

- 理解现有仓库并完成一个小功能修改；
- 定位并修复缺陷；
- 补充或修改测试；
- 在完整任务中进行局部重构。

每项任务保存仓库版本、任务描述、允许的工具、测试命令和人工验收标准。重点观察图方法是否改善步骤规划、模型选择或工具选择，而不只统计某一步的 token 节省。

### 3.2 办公场景

**首个原型建议选择“论文阅读摘要与自动归档”。** 录音明确提到该流程重复且操作相对固定；团队可以用自己日常阅读的论文试用，比较摘要准确性、归档正确性和人工修改量。邮件及日历联动可列为第二批候选，先核实账号授权、接口和实际操作边界。

| 筛选维度 | 通过标准 |
| --- | --- |
| 真实需求 | 有同学愿意在日常工作中连续试用，任务不是为演示临时编造。 |
| 可验证性 | 能保存输入、输出、过程记录和明确的完成标准。 |
| 可接入性 | 目标工具允许在关键步骤插入方法并观察其效果。 |
| 代表性 | 包含多步决策或重复操作，能体现方法的适用条件。 |
| 数据与成本 | 不依赖不可获得的企业数据；权限、采集和模型成本可控。 |

## 四、初步技术实施方案

先把“图方法”定义成**可测试的独立模块**，不要预先假定某个具体图算法已经成立。根据讨论，它可能用于任务状态表示、工具或模型选择、步骤规划。第一轮实验只选择一个清晰的介入点，其他条件保持一致；证实有效后，再组合多个介入点。

1. **任务入口：** 接收代码或办公任务，记录上下文、可用工具和完成条件。
2. **可控决策层：** 在选定节点调用图方法，输出下一步、工具或模型选择，并保存图状态及决策依据。
3. **执行层：** 由智能体或工具执行动作；记录失败、重试、回退和人工介入。
4. **观测层：** 统一记录调用次数、输入与输出 token、费用估算、端到端耗时和任务结果。
5. **对照开关：** 对同一任务切换“直接模型／原有流程”“仅用提示或 Skill 引导”“图方法实际介入”三条路径。

### 必须先做的接入可行性试验

录音中反复讨论了代码工具的接口限制。需要实测目标工具能否在规划、模型选择或工具调用前取得控制权，完成路由后继续执行，并留下可核对的记录。**不能把“写一段 Skill 让大模型读懂”直接等同于方法已经控制了路由。**

如果常用代码工具的扩展点不足，先用可控的开源智能体或自建执行层验证方法，再评估接回同学日常工具的成本。具体工具和 API 能力应以官方资料和最小实验核实。

## 五、实验与评价设计

### 5.1 对照组

- **基线 A：** 直接调用同一模型，或使用当前原有智能体流程。
- **基线 B（补充）：** 仅用提示词／Skill 描述方法，让大模型自行遵循。
- **实验组：** 图方法在预定决策点真实介入。

相同任务下固定模型版本、工具权限、任务输入、运行环境和预算。每类任务做重复运行，记录随机波动与失败原因。这样才能区分“图方法本身的收益”和提示词、模型、工具差异带来的收益。

### 5.2 任务来源

一部分使用与实际工作相符的公开任务集，便于复现；另一部分来自同学真实的代码和办公工作，匿名整理后保存任务来源与构造方式。公开任务集如果与真实工作明显不符，应降低其在结论中的权重。办公任务即使没有现成数据集，也可先真实试用，但需要保留可核对的样本和人工反馈。

### 5.3 指标

| 维度 | 具体指标或记录方式 |
| --- | --- |
| 任务完成与质量 | 代码：测试通过率、需求满足度、人工审查及回归问题。办公：摘要准确性、归档正确率、遗漏和误操作。 |
| 效率 | 端到端耗时、模型与工具调用数、重试次数、人工修正时间。 |
| 资源成本 | 输入与输出 token、按实际价格计算的费用；分别报告局部步骤和整项任务。 |
| 真实使用 | 试用人数、完成任务数、复用意愿、失败原因和典型反馈。 |

质量评审先制定评分规则；可以用大模型辅助判分，但关键样本要人工复核，适合时采用盲评。报告均值、波动和失败案例，避免只展示成功演示。

录音里的“节省约 10%”更像说明价值的例子，**不是已经确定的验收门槛**。建议跑通首轮基线后，再与导师确认质量不退步、成本和时延改善多少才算有效。

## 六、分阶段实施与交付物

| 阶段 | 要做的事 | 可交付成果与转段条件 |
| --- | --- | --- |
| 0 需求校准 | 明确图方法的首个介入点、目标工具和首批试用者；核对转写疑点。 | 一页方法定义、场景清单、待验证假设。 |
| 1 接入试验 | 验证能否在关键步骤前后稳定接入，并记录方法输入、决策和执行结果。 | 最小技术样例；若无法接入，立即切换可控执行层。 |
| 2 最小原型 | 实现一个代码任务流和一个办公任务流，支持同学真实试用。 | 可运行原型、简明使用说明、日志结构、首轮问题清单。 |
| 3 对照评估 | 建立基线和任务集；收集指标、真实反馈与失败案例。 | 对照数据、案例分析、是否继续投入的判断。 |
| 4 扩展 | 在方法有效且接入可行后增加流程，考虑统一平台。 | 更完整的产品与研究计划。 |

讨论中提出尽快做出可用原型、让同学在节前试用的目标。具体日程要结合人员和假期安排重新确认；先保障**有人能真实用、能留下对照数据**，再扩充功能。

## 七、现在就可以开展的调研任务

1. **写清方法。** 明确图的节点、边、状态更新和决策输入输出，以及与普通提示词或路由器的区别。
2. **查接入点并做最小验证。** 针对目标代码工具，逐项验证规划、模型选择和工具调用前后能否插入逻辑；不要只看宣传或帖子。
3. **收集真实任务。** 找试用同学收集代码任务与文献整理任务；检查公开任务集的代表性。
4. **建立基线与评分表。** 先让直接调用模型的方案跑起来，制定代码和办公任务各自的成功标准和日志字段。
5. **确认分工与资源。** 明确参与同学的时间、设备、模型预算；把场景试用、接入验证和评估设计拆成可并行的小任务。

## 八、待导师确认的问题与转写疑点

| 问题 | 建议确认的内容 |
| --- | --- |
| 核心研究贡献 | 主要是图状态表示、工具／模型路由、规划，还是它们的组合？第一轮优先证明哪一点？ |
| 首个主实验 | 代码必须覆盖；先用代码做主实验，还是先用文献整理打通完整闭环？ |
| 目标工具 | 录音中 Codex、其他代码工具及若干模型名称转写不清；实际使用哪些工具与版本？ |
| 接口与收益说法 | 某路由工具“能接入”及“约 50%”收益只是未核实的帖子转述；原始资料是什么，能否复现？ |
| 资源与时间 | 哪些同学能参与试用或开发？模型预算、设备和节前试用安排如何确定？ |

---

**建议的第一步：** 先完成“方法定义 + 目标工具接入试验 + 两类真实任务各 5—10 个样本”。这三件事能最快判断当前方向是否既可实现又可验证；样本数是初步工作建议，不是录音中的硬性要求。
