# SSS 六类 MCP 应用内实测：阶段性结论

**研究问题。** MCP 的结构化返回能否让 MotifAgent 可靠复用工具步骤、减少模型判断，并降低合格科研交付的成本？本轮先把旧的跨应用合成资料与真实应用接口分开：对文献发现、Zotero、Obsidian、本地 Python／Quarto、Gmail、Google 日历分别检查类内调用链，并在有自然任务的地方做 Agent、脚本或 Motif 对照。

**最清楚的新结果来自日历。** 在专用「SSS MCP Test」日历上，普通脚本对三道合成排期题 **3/3 正确、0 次模型请求**。初轮 DeepSeek Flash Agent 虽读对占用，交付却 **0/3 通过时段约束**，11 次模型请求、估算 API 费用 US$0.01024213。于是我们给日历 MCP 加入只读的最早空档计算和候选校验工具，保持 A/B 原提示与事件版本，在 C 题新增一段会使旧答案失效的占用。真实 MCP 验收显示工具三题计算正确，Agent 也实际调用两个新工具，最终 **3/3 通过时长、窗口、冲突和最早条件，来源事件 ID 齐全**；代价是 12 次模型请求、估算 US$0.01248631、47.448 秒。两轮价格均按本机价格表估算，未与供应商账单核对；C 的来源已变，不能把三题总费用差当成严格同题因果估计。这个结果表明：**字段有结构、工具能调用，不等于模型会算对；将明确时间约束交给工具可修复本轮交付，但未产生模型费用节省，也没有超过简单脚本。** 测试事件是合成夹具，不能当作真实科研会议需求。

**其他门类的边界同样明确。** Gmail 已在不同真实提醒邮件上核验 `search→read` 局部跳过一次模型请求；探索性三题从 9 降到 6 次请求，缓存计价估算费用仅下降约 2.43%，且答案未独立盲评。Zotero 和 Obsidian 的已批准资料各出现最多一轮可尝试接管的读取链，但尚无在线 Motif 对照，简单脚本已能完成相同结构读取。固定公开 CSV 的复算和 Quarto 交付也已由零模型脚本完成。文献发现 Agent 找对了预印本与期刊版的主引用方向，却把未读到的预印本正文说成已核对的版本差异，完整文献卡未过证据质量门。

**当前判断与下一步。** 目前能报告“真实 Gmail 局部跳轮”和“日历内确定性工具把这组三题 Agent 的时段答案修到 3/3”；**不能报告 Motif 已降低合格科研交付总成本**。对确定性子问题，简单脚本是强基线；Motif 的候选价值应集中在跨不同任务的参数重绑定、来源版本变化时的局部失效和安全恢复。下一步用不同真实科研决定先盲评交付质量，再同题比较普通 Agent、脚本／缓存和 Motif 的核账费用、人工修订与耗时；新反证必须能打断旧路径。若脚本已同质完成，主动缩小 Motif 主张。
