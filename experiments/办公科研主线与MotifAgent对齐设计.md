# SSS 主线修订：办公／科研工作流与 MotifAgent 对齐

> 2026-09-25 修订。设计稿，尚非效果结论。**MotifAgent 是运行内核，效果第一，具体机制第二**。冻结源码只读，在 SSS 内复制必要模块、删减并适配。G-Agent 与 AutoTool 是可选的局部参照，三者无需全部兼容。Jev 尚未接入，也没有 Jev 实测成绩。

## 1. 产品任务与研究问题

首个交付任务定为**有范围的课题组调研交付与增量更新**：同学给出研究问题、时间与来源范围、报告读者和验收点；软件收集或导入资料，建立来源和证据台账，产出可审阅的对比报告；新资料到来时只重查受影响的结论与段落。输出至少包括来源清单、逐项证据表、报告、未解决问题和本次变更记录。这是一个完整的科研办公任务，不是单篇论文摘要，也不是只回答若干问答题。

选它的原因是课题组可反复用，而且“检索／导入 → 去重 → 读取 → 抽取 → 证据绑定 → 交叉核对 → 写报告 → 增量更新”的依赖链可观察。真正需要语义判断的地方是来源相关性、互相矛盾的证据、覆盖条件是否满足以及综合写作。结构层能否在质量不下降时减少重复执行、完整模型请求和人工核查，是待检验假设；减少可见上下文长度是另一项须单独验证的取舍。代码迁移保留为第二条任务线，复用同一运行时、语义接口和测量体系；不要让两个场景同时驱动首版产品界面。

**取舍规则：**先从公开及自建 benchmark 冻结任务和验收，并用最简单的脚本＋生成模型建立基线。SSS 正式路径以迁移后的 MotifAgent 为内核；只实现解决重复读取、重复决策或恢复失败的相关 motif 能力。若 MotifAgent 路径未比简单基线更有用，应如实报告失败并缩小机制主张；若 Jev 判断不改善结果，保留接口但不启用 Jev。

首个试点建议限定为“给定主题和 5–15 份可公开论文／文档，产出 1–2 页组会前调研简报；一周后加入 1–3 份新材料并更新简报”。首批还不做开放互联网的无限搜索、自动发邮件、自动改共享文件或整库重写。检索网络可以作为有边界的工具接入，并记录检索范围与时间。受版权或保密限制的文档先只在本机保存；外部模型调用前应在界面说明将发送哪些摘录。

## 2. MotifAgent 是主参照，借的是执行机制

本地 MotifAgent 的关键路径是：历史轨迹和工具 schema 构建 motif；motif 携带工具 DAG、参数链、守卫与并行层；运行时持有 `MotifFrame`，在阻塞时产生显式 handoff，只给语义层有界的 read-set／槽位／候选，随后按依赖签名重新进入结构执行。原实现还可把已完成 motif 投影成紧凑状态；在 DeepSeek 云 API 上，这种投影若重写已有会话前缀，可能使便宜的缓存命中变成较贵的未命中，因此不作为默认节省机制。SSS 已迁入 `MotifFrame`、依赖签名、证据绑定和 handoff，在合成办公题及公开研究题的来源层运行；`src/graph/runtime.py` 仍驱动研究题下游检索与综合。完整执行器、跨任务挖掘和 serving 等能力按 benchmark 结果决定迁移范围。

| 候选机制 | 何时值得实现 | 必须证明的效果 |
| --- | --- | --- |
| 可执行 motif | 相同资料处理步骤确有跨任务重复，且普通脚本难以处理分叉或恢复 | 同一 motif 在不同资料上复用，质量不降且省人工／模型成本 |
| 参数与证据流 | 来源变化导致旧结论误用或重复核对 | 上游资料变化后，仅下游受影响结论失效；更新正确且省时 |
| 有界语义交接 | 开放式 Agent 在局部候选选择上反复读上下文或犯错 | 模型无效、低置信或越权时可停；合格交付成本下降 |
| 中断／恢复 | 增量更新或失败重试成为真实高频需求 | 有效结果不重做，失效结果不误用；端到端收益可测 |
| 上下文投影 | 窗口压力、证据噪声或实测的缓存计价后费用与合格率确有改善空间 | 默认保留稳定前缀；单独消融，计入缓存失效、摘要／找回和人工复核，不能把 token 降幅冒充结构执行收益 |

AutoTool 的工具顺序和参数依赖可用作**局部候选生成／校验**；仅凭高频工具转移不授权执行。G-Agent 的全计划与 tiny-edge 复用可用于后期跨任务挖掘；首批轨迹不足时，先用人工审核的 motif 模板加运行记录，不宣称自动挖掘。MotifAgent 的 serving 调度和 KV 保留依赖特定后端，本机使用云 API 时只记录可测量的调用／缓存结果，不宣称实现了后端优化。

**云 API 的成本顺序**：先争取在证据守卫下省掉完整模型轮次和失败重试，再减少无必要的输出与重复生成；在不破坏已建立前缀的地方控制新进入上下文的材料。对旧历史做摘要或在每步换工具 schema，必须单独测后续缓存命中率、未命中输入、输出、摘要调用和质量。工具集合可以按任务静态预选；若按步骤动态更换，应证明它比稳定集合在同题合格成本上有额外收益。详细执行门见[缓存感知的结构执行与 MCP 任务计划](缓存感知的结构执行与MCP任务计划.md)。

## 3. 首个任务的执行图

```text
任务约束与验收点
  → [来源快照] 导入／检索、去重、记录版本和权限
  → [证据读取] 按必答点定位段落并保留原文与页码
  → [证据表] 每个条件绑定支持、反例、冲突或缺口
  → [报告草稿] 只引用证据表中已核验的条目
  → [质量门] 人工逐项看引文是否蕴含结论、是否漏关键条件
  → [增量更新] 新来源或旧来源变化后重算受影响子图
```

每一步都有 `input_digest`、`output_digest`、来源、时间、工具版本、费用和状态。`quality_gate` 中的机器检查只能证明来源／引文可定位和结构覆盖，**不能声称证明结论真实或充分**；首次试点用人工评审作为最终质量门。正式写入组内共享位置需要用户确认预览；本机草稿可直接保存。输入是动态资料时，应同时保存查询时间、搜索结果和失败检索，避免只保留成功来源。

上述是产品流程，**不是必须全部转成 motif 的实施清单**。任务主循环由 MotifAgent 持有；其中 `source_snapshot`、`evidence_read`、`incremental_refresh` 哪些需要独立编译 motif，由 benchmark 中的重复和恢复瓶颈决定。报告草稿由生成模型完成，结构运行时负责可核验的来源／引用边界。代码迁移后续映射为 `repo_snapshot → callsite_discovery → candidate_patch → test → review`，按同样效果门槛取舍。

## 4. Jev 预留为有界决策器

运行时定义稳定的 `BoundedDecisionPort.evaluate(batch)`，而不是把 Jev 写进 motif 节点。一个 batch 共享同一份已裁剪、已脱敏的状态，包含若干原子问题；每题记录 `question_id`、`kind`（choice／score／noul）、候选及定义、证据 ID、输入签名、可接受的回退条件、调用预算。返回值记录模型固定版本、原始概率／置信度、用量、耗时和错误。运行时负责验证候选仍存在、签名未变化、阈值是否经过验证，以及写操作是否另需确认。概率不是事实证明，也不替代引文核验。

首批 Jev 候选点只有两个：① 对**已有**候选来源／段落做相关性筛选；② 对证据表中的冲突或缺口做分类。Jev 不负责生成新查询、写报告正文、自由编辑文档或决定未经核验的工具参数。语义接口将来可接 `DeepSeekDecisionAdapter`、`JevDecisionAdapter` 与记录回放器，使“有无 Jev”的结构执行保持一致。Jev 出现低置信、候选外回答、超预算或服务错误时回退到同一受限生成模型／人工复核，并把回退全部计入成本。**先保留数据契约，不在首版接入无评测价值的 Jev 调用。**正式试验前固定模型 ID、阈值和中文／英文校准集。

TypeSafe 当前公开 API 是 `POST /v1/systemone`，使用 `state`、`model` 和带 ID 的 `questions`；Choice 返回选项、概率和置信度，Score 和 Noul 是另两种题型。其文档说明英语效果最好，中文办公材料需单独验证。API 形状与价格可能变化，正式接入时重新核对：[API reference](https://docs.typesafe.ai/api)、[Models](https://docs.typesafe.ai/models)。

## 5. 验证方式与先后顺序

主任务先收集 5–10 个课题组真实、允许评测的调研需求，冻结来源快照、问题、交付格式和人工评分表。第一阶段只比较最简脚本＋生成模型与原生生成式 Agent，确定可用性和主要成本；结构机制出现后再加“结构运行时＋同一生成模型”；Jev 实际可接入且有合适决策点后，再加 Agent＋Jev 与结构运行时＋Jev。各组尽量保持同一生成模型、检索权限、来源集合、预算和人工评分；不使用假响应伪装 Jev 成绩。事后改提示或守卫的题目进入开发集，不能继续算留出题。

首要指标是**人工判定的合格交付率、每份合格交付的总费用、人工修订分钟数、端到端时间**。同时记录来源遗漏、错误引文、条件漏答、增量更新正确率、重复模型调用、缓存命中／未命中 token、Jev 调用与回退。对于未合格任务，记录耗费与失败类型，但不拿低价的失败结果计算“省钱”。在完整对照具备后，结构增益看“原生 Agent 对结构无 Jev”和“Agent＋Jev 对结构＋Jev”；Jev 增益看两个结构组；另与普通脚本比较额外复杂度是否值得。

### 近期里程碑

1. **benchmark 冻结**：先使用 [DR³-Eval 中文任务](../benchmarks/dr3_zh003/README.md)评价研究报告，使用[自建两阶段小题](../benchmarks/office_research_v0/README.md)评价归档和增量失效；再引入课题组真实任务。现有逐项论文问答降为证据子模块。
2. **MotifAgent 内核迁移**：复制冻结源码中必要的 frame、证据、执行、handoff 组件，保留来源和许可；以研究资料入库、证据表、报告草稿与增量更新为首条端到端链。简单脚本和 DSH 原生 Agent 是同题基线。
3. **瓶颈驱动的机制实验**：在迁移内核上只强化 benchmark 暴露的重复或恢复瓶颈，并逐项消融。G-Agent、AutoTool 只在对应瓶颈出现时考虑。Jev 数据契约先固定，真实 API 在有合适有界决策点后接入。
4. **小组试用和产品判断**：让至少 3 名同学各完成一次任务，记录人工修订、可理解性和复用意愿。若结构或 Jev 未改善合格率、合格成本或修订时间，就不放入默认产品路径；若普通脚本已足够，优先选简单实现。

## 6. 本次修订对现有原型的判断

已完成的论文问答、引文校验和两项窄代码迁移样例是**子模块与安全边界样例**。2026-09-25 已从冻结 MotifAgent 源码迁入 frame、证据、依赖求解、handoff 与候选挖掘，并在合成办公科研 A→B 任务上跑通归档、暂停恢复、来源复用和旧结论失效。随后从两份真实论文的工具轨迹编译出一个只读资料读取 Motif，经第三份论文留出核对后在新资料和增量任务中执行；这个切片仍不等于通用 MotifAgent 编译器。调研流程的规划、证据选择、综合已有 DSH 类型化交接，但还没有由 Motif 内核统一控制的完整真实资料报告闭环或 Jev API 调用。现有研究对照中多次出现部分答案，尚无“合格交付成本更低”的证据。下一步应停止围绕单篇论文继续事后调参，先完成公开研究报告质量对照和真实工作流。
