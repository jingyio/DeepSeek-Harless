# 测试日历上的应用内排期实验（2026-09-29）

**可向导师汇报的结论**：日历不必等待真实会议才可测试工具与结构机制。项目已有独立的「SSS MCP Test」日历；本轮在其中新增六个标明测试用途、无参与者和邀请的占用事件，构造三道不同日期、窗口与时长的排期题。真实 Google Calendar MCP 读回事件及忙闲，并通过固定 ID、更新时间和时间区间逐项核对。普通确定性脚本在三题上都找到正确的最早时段；初轮普通 Agent 虽正确读取占用，**0/3 份交付通过时间约束质量门**。加入只读的最早空档计算与候选校验工具后，Agent 在 A/B 同源题与 C 新增占用题上 **3/3 通过时段约束**，但模型请求与 API 费用均高于初轮，且简单脚本仍可 0 模型请求完成。**这些事件和任务是合成夹具，不能算真实科研排期或 Motif 节费成绩。**

| 合成请求（Asia/Shanghai） | 真实测试日历中的两段占用 | 最早可行时段 |
| --- | --- | --- |
| A：10 月 12 日，连续 60 分钟；窗口 10:00–12:00 或 14:00–17:00 | 09:30–10:15，13:00–14:00 | **10:15–11:15** |
| B：10 月 13 日，连续 45 分钟；窗口 15:00–17:30 | 14:30–15:30，16:15–17:00 | **15:30–16:15** |
| C：10 月 14 日，连续 90 分钟；窗口 09:00–13:00 或 14:00–17:00 | 10:00–11:00，14:00–15:00 | **11:00–12:30** |

脚本通过真实 MCP 执行 `list-calendars → list-events → get-event → get-freebusy`，共 **13 次工具调用、0 次模型请求、18.266 秒**。每题 `list-events` 的两条事件须与分别 `get-event` 取得的 ID、开始／结束和 `updated` 一致；`get-freebusy` 的忙闲区间须与两事件一致，才计算空档。中间一次尝试出现 `get-event` MCP 错误并停止，下一次新尝试全链通过；没有把失败隐藏为成功。原始返回及账号信息不入仓库，结果摘要和每次工具输入／输出哈希存于 `.local/benchmarks/mcp-app-internal-v2/calendar/script-baseline.json`。

为测可恢复的应用内字段视图，另建只暴露**这一个测试日历**的只读桥。它拒绝查询 `primary` 或其他 ID，并将日历列表缩为测试日历，事件只给 ID、标题、开始、结束、状态、更新时间和日历 ID；忙闲区间保留。相同 13 次工具调用和计算逻辑在该视图上仍得到三题同样答案，工具返回 JSON 文本总量从 **14,074 字节降到 5,963 字节（约 57.6%）**。其中日历列表由 2,486 降至 203 字节，主要是**收窄应用范围**；事件列表与事件详情合计由 10,571 降至 4,743 字节，才是任务所需字段投影。字节差不等于模型 token 或费用收益，也尚未由模型质量验证。

复现入口为 `scripts/setup-calendar-internal-fixture.cjs`（预览／幂等建立／仅清理匹配 ID 的测试事件）、`scripts/run-calendar-internal-script-baseline.py`（原输出或 `--scoped`）及 `scripts/calendar-scoped-benchmark-mcp.cjs`。测试日历 ID、事件版本、写入回执、原始账本和将来的 Agent 轨迹只保存在 `.local`。写入由评测准备脚本使用已有测试日历权限完成；Agent 只会得到受限只读桥，无法建立事件或读取其他日历。

## 同题普通 Agent：工具读对，三份交付均未过质量门

用户批准 A/B/C 三题的冻结只读预览后，分别运行 DeepSeek Flash，`reasoning_effort="off"`，每题最多 10 次模型请求／US$0.50，总上限 US$1.50。Agent 只见到本轮受限的**五项只读日历工具**及测试日历字段视图；没有准备或创建事件。原始提示、桥接源码哈希、逐请求账本与轨迹在 `.local/benchmarks/mcp-app-internal-v2/calendar/agent-{a,b,c}/`。三题均在预算内完成，但“模型结束”不等于排期答案正确。

| 题 | 模型请求／MCP 调用 | 用时 | API 用量估算费用 | Agent 交付与独立计算的差异 |
| --- | ---: | ---: | ---: | --- |
| A | 3／5 | 13.814 秒 | US$0.00359813 | 推荐 **14:00–15:00**；最早其实是 **10:15–11:15**。答案自己承认 10:15–12:00 空闲 105 分钟，却错误排除连续 60 分钟。首轮用 `primary` 请求的两次调用被受限桥拒绝，之后改用测试日历。 |
| B | 4／3 | 12.807 秒 | US$0.00319705 | 正文末尾推荐 **15:30–16:15** 正确，标题却写 **16:00–16:45**，后者与 16:15 开始的事件冲突。交付自相矛盾。 |
| C | 4／3 | 14.143 秒 | US$0.00344695 | 推荐 **09:00–10:30**，与 10:00–11:00 占用重叠；最早应为 **11:00–12:30**。答案列对忙区间却说重叠时段“完全可行”。 |

三题合计 **11 次模型请求、11 次 MCP 调用、40.764 秒、US$0.01024213**（由逐请求缓存命中／未命中与输出用量按本机价格表估算，未与供应商账单核对）。A 的两次被拒请求在轨迹中标为工具错误，不能将五次 MCP 调用全算作成功。没有访问其他日历或写入。`scripts/audit-calendar-internal-agent-answers.py` 从冻结答案提取标题与最终推荐，逐项检查时长、窗口、占用冲突和“最早”条件，判定 **0/3 合格**；完整判断仍需人工检查自由文本，自动审计不是领域盲评。原审计结果保存在 `.local/benchmarks/mcp-app-internal-v2/calendar/agent-quality-audit.json`。

**实际新增占用后的失效检查。** 在上述三题及 Agent 轨迹冻结后，只对 C 加入第七个测试事件，时间为 **11:30–12:30**，无参与者。重新经受限日历 MCP 读取三个事件、逐项固定版本并核对忙闲，使用 **6 次工具调用、0 次模型请求、12.254 秒**。原本正确的 **11:00–12:30** 与新事件冲突，脚本将最早推荐改为 **15:00–16:30**。前后事件 ID 数由 2 变 3，新占用与旧推荐确实重叠；版本和工具摘要在 `.local/benchmarks/mcp-app-internal-v2/calendar/{script-baseline-scoped.json,script-incremental-scoped.json,fixture-change-manifest.json}`。这只证明简单脚本在真实测试日历变化后能够重新计算，**不是 Motif 的在线失效／恢复成绩**。

这给出清楚的机制边界：**高度结构化的工具输出和字段剪枝，不能保证模型把时段算对。** 对这种明确窗口、时长和忙闲的子任务，应优先由确定性程序求可行时段并做交付前校验；模型只处理时间偏好、跨人沟通或研究安排含义。当前三题质量门未过，不能把未来可能跳过的模型请求写成“合格交付节费”。这组三题是同一测试日历中的合成诊断，不是独立真实科研决定，也不宜用 A/B 训练、C 留出后声称前瞻收益。下一轮还需在真实排期需求中验证这个分工，并让 Motif 接受来源变化后的失效检验。

## 日历内计算工具与复测

已在正式日历桥与受限测试桥加入两个只读工具：`find-available-slots` 依据一次实时 `get-freebusy` 返回最早连续空档；`validate-slot` 重新查询忙闲，分别给出时长、窗口、冲突、是否最早的检查结果。输入要求明确的日历 ID、IANA 时区、带 UTC 偏移的窗口和分钟时长；时区偏移不符、来源错误或忙闲查询失败时直接报错。返回查询时间与来源内容 SHA-256。两个工具都不能创建或修改事件；`validate-slot.valid` 仅表示候选可行，`isEarliest` 单独表示它是最早的。

本地测试覆盖 A/B、变化前后 C、相邻占用边界、短于要求的空档、旧 C 候选冲突、非测试日历、偏移不符与来源出错。真实 Google Calendar MCP 上，受限桥和正式桥都读回 A **10:15–11:15**、B **15:30–16:15**、新增占用后的 C **15:00–16:30**，并拒绝旧 C **11:00–12:30**。两条桥的只读验收均为 0 次模型请求、0 次日历写入；复现入口为 `scripts/check-calendar-availability-live.py`（正式桥加 `--production`），结果哈希与摘要保存在 `.local/benchmarks/mcp-app-internal-v2/calendar/availability-v1/live-{scoped,production}-smoke.json`。正式桥健康检查为 13/13 项工具、代表性只读调用成功。

Agent 重测沿用上一轮三题原提示，不把正确时段写进提示；A/B 的日历事件版本也与旧试跑一致。C 的来源有第七个事件，因此是增量变化诊断，不能当成同源 A/B 对照。三题预览、提示、工具源码哈希、来源版本、批准回执和预算账本分别保存在 `.local/benchmarks/mcp-app-internal-v2/calendar/availability-v1/agent-{a,b,c}/`。用户批准确切预览后，分别运行 DeepSeek Flash，`reasoning_effort="off"`，每题最多 10 次模型请求／US$0.50，总上限 US$1.50；仅访问受限测试日历，不写入或发送邀请。

**取舍很清楚。** 初轮 Agent 为 **0/3**，新工具试跑为 **3/3**；A/B 在相同提示和来源版本上改善，C 验证新占用后的正确恢复，但只有每题一次试跑，不能排除模型采样波动。初轮三题合计 11 次模型请求、40.764 秒、估算 US$0.01024213；新工具试跑多 1 次请求、6.684 秒、估算多 US$0.00224418。C 的来源状态不同，不应把总费用差额当成严格同题因果估计。简单脚本在这些合成题上仍是 **3/3、0 次模型请求** 的强基线。这证明把明确的时间运算交给工具能修复本轮 Agent 答案，却没有证明 Motif 省钱、跳过模型请求或优于脚本；后续须在真实、含偏好与沟通的排期任务中检验增量价值。
