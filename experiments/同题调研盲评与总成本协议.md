# 公开调研同题盲评与总成本协议

> 2026-09-25。此协议已接入程序，但尚无多方法真实合格报告成绩。

## 为什么需要这一步

三条可运行入口是普通检索脚本、Motif 逐项调研和原生 DeepSeek Harness Agent。它们的提示、工具和调用次数可以不同，但必须读同一问题、同一必答项和同一来源快照。人工评审分别判定严格合格与小幅降质可用两档；每一档只比较通过该档的交付费用。失败结果再便宜也不算节省。

目前三个入口均保存 `question.txt`、`answer-points.json`、`sources.json` 和 `status.json`。`score-research-trial.py` 用文件名与 SHA-256 生成共同来源摘要；任一题目、必答项或文件哈希不同，整组评分停止。2026-09-25 对 DR³-Eval 中文 003 的**无模型预览**，三组来源摘要均为 `3d53c2058bc66da09ac5dc7e6346bb194ad3c901ced528f95738705c4a1d3b63`，覆盖 16 份来源。这证明输入快照相同，不证明输出质量相同。

## 运行与盲评

1. 冻结任务题目、资料、补充必答项、模型、预算和允许的工具。DR³-Eval 中文 003 已用于开发，应作为开发题；主要效果结论需新留出题。
   如果问题本身允许“现有证据不足，暂不判断”，在冻结必答项时显式写 `allow_abstention: true`。运行时把这种答案标为 `abstention_pending_review`，评审仍需核对来源确实不足；不能事后为某一方法的缺答添加该标记，三组必须使用同一份必答项。
2. 用三个入口分别运行。普通脚本的人工检索词和准备时间要记录；原生 Agent 的多步请求设置 `--max-model-requests`。`--call-model` 才会产生付费调用。
3. 协调者给运行结果分配匿名代号 A/B/C，私下保存代号与方法映射。所有方法用相同的 **brief-only** 材料格式，评审拿到同一来源快照：

   ```bash
   .venv312/bin/python scripts/prepare-research-review.py /path/to/run \
     --question-file /path/to/query.md \
     --answer-points benchmarks/dr3_zh003/answer_points.json \
     --label A --brief-only --out .local/research-trials/review-A.md
   ```

   这种模式不依赖某个方法特有的证据 JSON，因此也可给原生 Agent 的自由格式答案出材料。保留原回答文本，评审可能从写作风格猜到方法，匿名代号不能保证完全双盲。评审应核对原文是否支持结论，而不是只看是否有页码。
4. 每位评审填写机器可读取的评分表。先生成模板：

   ```bash
   .venv312/bin/python scripts/score-research-trial.py template \
     --answer-points benchmarks/dr3_zh003/answer_points.json \
     --label A --out .local/research-trials/review-A.json
   ```

   每项填事实与引文支持 0–2、要求覆盖 0–2、是否有重大错误、实际修订分钟数；比较题还填方法异同是否准确。评审同时填写 `overall_usable`（无需补全即可直接使用）和 `practical_usable`（允许一个次要缺口后仍能用于当前研究决定）。首轮只支持每组一份评审表；多人评审需先约定争议仲裁，不能暗中取有利分数。

   **严格档**保持原规则：所有必答项的支持与覆盖均为 2、无关键错误、整体可直接使用，比较题的异同准确。**小幅降质档**是额外报告的容忍界限：所有已陈述事实都必须得到充分来源支持（每项支持为 2），不能有关键事实或来源错误；至多一项要求只达到部分覆盖（1），其余覆盖均为 2；比较题的核心映射与异同仍须准确，评审明确认为输出可用于当前决定。缺失完整数值表、错误归属运行、将没有来源的推断说成事实，不能仅按措辞问题放行。评审要记录实际人工补写或更正所用时间；成本对照不得把修订时间当作零。

## 费用与汇总

协调者在被忽略的 `.local/` 写试验清单。`setup_minutes` 必须显式填写，包括零；它包含准备检索词、提示及人工设置时间。实际 API 费用需写 `api_cost_usd` 和账单证据引用；仅有 token 用量时程序只给**按 2026-09-25 固定价估算的范围**，不将其算作完整总费用。本地运行费用和人工时薪分别填 `local_cost_usd`、`human_rate_usd_per_hour`，缺任一项则总费用标为未完整记录。

```json
{
  "schema_version": 1,
  "task_id": "dr3-zh003-development-v2",
  "answer_points": "/Users/apple/Desktop/SSS/benchmarks/dr3_zh003/answer_points.json",
  "human_rate_usd_per_hour": 12,
  "runs": [
    {
      "label": "A",
      "method": "ordinary_script",
      "run_dir": "/absolute/path/to/real/run",
      "review_file": "/absolute/path/to/review-A.json",
      "model": "deepseek-flash",
      "api_cost_usd": 0.02,
      "api_cost_evidence": "provider bill reference",
      "local_cost_usd": 0,
      "setup_minutes": 5
    }
  ]
}
```

示例金额和时薪只是**字段示意**，不能作为实际实验数据。填完所有运行后执行：

```bash
.venv312/bin/python scripts/score-research-trial.py score \
  --manifest .local/research-trials/trial.json \
  --out-prefix .local/research-trials/result
```

得到 `result.json` 与 `result.md`。程序分别输出 `qualified` 和 `practical_qualified`，只在对应档人工通过且总费用字段完整时给出该档交付费用；若任一组不合格，明确标记不能以其低费用宣称该档增益。`fixture_only` 的合成报告被拒绝作为真实运行评分。允许小幅降质不等于已证明效益：还要报告人工修订后的总费用、端到端耗时和与简单脚本／缓存的对照。

后续将 mu 与 KnoxChat 纳入时，需给它们也保存同格式的题目、必答项、来源清单、实际回答、模型用量及账单证据。KnoxChat 主场景是代码迁移；若拿它测调研任务，需先确认该扩展确实支持所需文件与研究工作流，不能把不适用工具的失败当成 SSS 胜利。
