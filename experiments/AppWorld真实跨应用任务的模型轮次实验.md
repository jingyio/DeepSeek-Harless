# AppWorld 真实跨应用任务的模型轮次实验

2026-09-27。**任务对象是官方 AppWorld 环境中的原生多应用任务**。此前核查 AppWorld coverage 图表的任务只读取本地 CSV／JSON／SVG；它检验资料复算，不能当作 AppWorld 多应用 Agent 实验。官方环境同时提供交互式 Python 代码执行、应用 API 和 MCP 入口，适合在相同任务状态上比较两种工具交互形式。[AppWorld 官方仓库](https://github.com/StonyBrookNLP/appworld)

## 要检验的命题

Motif 的收益单位是**被安全省掉的模型决策或代码生成轮次**，不是少调几次应用 API。一个模型生成的 Python 程序可以在内部调用许多 API，因此“少了五次 MCP 调用”在代码 Agent 面前没有说服力。要检验的是：对多个不同任务反复出现、参数由当前应用状态绑定的局部程序／API 子图，运行时能否直接执行已见证的结构，省掉模型重新写同一段代码或逐步决定同一串调用，并在状态变化时正确交还模型。

## 公平的四个条件

在相同 AppWorld 任务、初始数据库、应用 API、DeepSeek 模型和任务期限下运行：

1. **直接工具基线**：Agent 逐次调用 AppWorld MCP 工具。
2. **代码基线**：Agent 使用官方 `world.execute` 一类代码入口，允许一个程序调用多个应用 API。这是必须战胜的强基线。
3. **简单复用基线**：代码 Agent 可调用已有函数／脚本、缓存与稳定提示前缀；包括与 Motif 相同的预取或 API 批处理便利。
4. **Motif 条件**：前两项独立训练任务的正常执行轨迹编译出局部、带参数流和状态守卫的算子；在未参与编译的任务上匹配并执行。需要新语义判断、参数无法绑定或执行失败时交还同一个代码 Agent。

直接工具与代码条件回答“API 调用形式本身影响多少”；**Motif 对简单复用基线**才回答图运行时是否有额外价值。可以另做“代码经 MCP 代理”的传输条件，记录额外延迟，但不能把换传输带来的差值归功于 Motif。官方仓库说明 `world.execute` 可通过 MCP 代理调用同一 API；MCP 路径需要显式保存环境状态。[官方 MCP 说明](https://github.com/StonyBrookNLP/appworld#-introducing-appworld-mcp-server-and-client)

## 轨迹、编译与执行边界

代码入口内部的 API 子调用必须记录为带 `task_id`、执行轮次、代码哈希、调用参数、返回值、应用状态版本和最终状态差异的事件。否则只看到一次 `execute(code)`，无法判断哪个 API 输出绑定下一次调用的哪个参数，也无法编译局部 Motif。不要从代码文本相似就推断可执行复用。

先按场景族冻结至少三项**不同任务**，两项用于发现候选、第三项留出。优先筛选跨两个以上应用、存在实际数据依赖且有相似局部操作的任务；不要把同一任务的重试算作独立样本。候选的输入槽必须在新任务由当前状态、上游返回值或模型明确交接填充；只允许 API schema 与当前状态能验证的结构执行。执行写操作时每个条件使用独立的任务世界；记录预期与非预期状态变化，失败或歧义时停下，不重复提交非幂等动作。

## 成功与否的判据

- 先看官方状态评测的完成率和附带损害，再看人工抽查的行动正确性；不合格任务不计作低成本成功。
- 逐轮列出模型请求：被 Motif 安全替代、仍需语义判断、错误跳过、回退与重试。报告缓存命中／未命中输入、输出、实际费用、端到端耗时、代码执行与 MCP 调用数。
- 若代码 Agent 已把重复 API 调用写成一个短程序，而 Motif 只减少 API 次数、没有减少模型请求或合格交付成本，就承认代码复用足够。
- 若 Motif 的匹配／守卫能在不同任务和状态变化下省掉代码重新生成或反复修复的模型轮次，且明显优于简单函数／缓存，才把它视作结构执行增益。此结果仍不能直接证明科研主线收益；科研主线另在 Zotero／Obsidian／文献发现的真实任务上验证。
