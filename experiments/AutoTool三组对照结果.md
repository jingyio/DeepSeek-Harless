# AutoTool 方法题：原生 Harness、普通脚本与结构流程对照

> 2026-09-24。题目、材料、人工核对项与三组配置在首次模型调用前记录于[题目登记](AutoTool三组对照题目登记.md)。本次各组只运行一次；以下是诊断结果，不是统计结论。

## 同题与运行边界

三组只使用 SHA-256 为 `9ef6334e6f2fcb7facf6aac97fd1a2a5888e02b9bd9ee55d1569f0238507980e` 的 [AutoTool PDF](../reference/AutoTool.pdf)，回答 TIG 的结构、工具选择、参数填充、回退与更新。统一使用已配置的 DeepSeek 官方 API、`deepseek-flash`、关闭模型推理。原生 Harness 能自行调用本地工具；普通脚本由固定检索词选取四段证据并综合一次；结构流程以可执行的规划、证据选取、综合三步处理。三组的工具自由度、格式和单次输出上限不同，不能归因为单一算法差异。

原生 Harness 的运行工作目录只放一份该 PDF，禁用了网页工具；它仍有本地 `bash` 工具。**工作目录副本不是操作系统沙箱**：运行轨迹确实显示它探查了工作目录以外的可执行文件路径，并将 PDF 抽取文本写到 `/tmp`；材料使用范围由提示词约束，不能当作强制文件隔离。它首先尝试系统的 `pdftotext`，发现缺失后改用 Python `pypdf` 抽取，多次读原文，再开始写长答。脚本组与结构组使用同一份 PDF 的预先抽取文本。这里的“原生”是未使用本项目的研究脚本，而非未加任何工具权限约束的 WorkBuddy，也不是 WorkBuddy 的直接性能测量。

## 诊断与结构—语义分离的下一步

本轮失败点能定位到不同边界：原生 Agent 的自由工具循环在 PDF 读取和长答上花费了 16 次模型请求；普通脚本的固定证据窗口把必答段落裁断；多步流程虽有来源核验和节点边界，却没有把用户问题的每个必答机制变成**运行时可核验的完成条件**。结构流程的 `selected-evidence.json` 已选到 AutoTool PDF 第 5 页，摘录中包含第三种启发式填充，但最终答案仍把它列为“不确定”；因此仅改检索词或多塞原文不能充分解决遗漏。

下一轮应在现有图运行时中加入任务级覆盖节点：规划后形成待答机制清单；来源节点给每项绑定可核验页码与原文片段；综合节点只负责语义概括；完成守卫检查每项是否有可回溯的结论与支持证据。若缺失，先回到相应证据或语义节点进行**有界修复**，记录额外请求和累计成本；仍缺失就明确停止。这个方向与 AutoTool 的“历史结构执行、低置信时回退”思想有相似性，但任务级证据覆盖图是本项目待实现的设计推论，不能说是 AutoTool 已提供的功能。

验证时应另取未用于设计的文献题，固定同一 PDF、答案标准与总预算，再比较原生 Agent、普通脚本、当前三步流程、加入覆盖守卫的流程。至少报告一次成功任务的总费用、人工修订量、页码/引文支撑情况和误报/漏报；只有完成这些，才能谈“效率增益”。
